先建立这个系统的地图感

这节课先给 swarmforge/ 画地图。你要把它看成“共享底座 + 可运行流水线”的编排层，看清 main 和 pack 分支怎么分工，目录里三件套各管什么，一次任务在仪表盘上怎么走。

先记住一句总判断

main 是共享操作系统。不能在上面直接 ./swarm。

README 的 Intent 写得很直：main 负责说明系统，并携带共享脚本和默认宪法条款。可运行的角色提示、本机宪法和 swarmforge.conf 在 pack 分支上。你点开的 swarmforge/ 在 main 上只有三样：宪法文章、交接协议、脚本。

第一层：先分两个世界

main = 底座

共享 swarmforge/scripts/、三篇核心宪法，以及 handoff-protocol.md。pack 不许用同名文件覆盖这三篇。

pack = 工作流

two-pack / four-pack / six-pack 各自带 swarmforge.conf、roles/*.prompt 和 local-*.prompt。这才是「这群 agent 怎么排队」。

合成器是 get-swarm-forge

它先拉 main 的共享件，再叠你选的 pack。可运行目录是合成结果，不是单纯 checkout main。

simple-windows 不是 pack

它是 main 上的 tag：每个角色一扇 Terminal、没有仪表盘。不要把它当 BRANCH= 传给 getting-started。

第二层：main 上的 swarmforge/ 三件套

位置 你可以怎么理解它 当前读法

工作流规则

Worktree 纪律
  • 启动时查明并记住分配给本角色的分支或 worktree。
  • 若分配的 worktree 是 master：在主项目检出的当前分支上工作；不要指望或创建 .worktrees/<role>。
  • 只在分配给你的分支或 worktree 里工作。
  • 除非交接里点名了某分支，或用户明确指示，否则不要检查、diff、合并或以另一条分支为基底。
  • 不要从 agent 的 worktree 里跑 ./swarm 去修 helper。若 PATH 上没有交接脚本，停下来报告启动失败。
宣告
  • 不要在宣告或签到评论里加角色署名。
提交说明
  • 每条 git commit message 都要带角色署名，格式：By <role>.
  • 例子：

Implement handoff validation

By coder.

  • 若漏写，commit-msg hook 会补上 By <role>.。不要跳过 hook（--no-verify）。
临时文件
  • 临时文件用本角色 worktree 里的 ./tmp/，不要用 /tmp。
  • 解析和 dry-check 写到 ./tmp/…。交接草稿也写在 ./tmp/。
  • 不要把 .swarmforge/handoffs/outbox/tmp/ 当草稿纸；那是交接 helper 用的。
失败条件
  • 若预期的 git 布局或分配的 worktree 不存在：停下来报告，不要默默在错误的地方干活。

交接规则

发送交接
  • 在本角色 worktree 的 ./tmp/ 里写一份只有结构化头的草稿，然后运行 swarm_handoff.sh <草稿文件>。
  • swarm_handoff.sh 会拒绝 /tmp 和 .swarmforge/handoffs/outbox/tmp/ 里的草稿。
  • swarm_handoff.sh --help 打印用法。不要把 --help 当成草稿路径传进去。
  • 只允许这两种消息类型：git_handoff、note。
  • 除非用户、角色 prompt 或宪法明确要求，否则不要发 note。
  • 被歧义、矛盾、或测试/规格冲突卡住时：用 pack_dashboard_request.sh clarify ./tmp/question.txt 问操作者。不要在窗格里问。除非上面那些权威明确要求，否则不要为此发 note。
  • 对 git_handoff：先提交，再写草稿。helper 从发送方 worktree 的 HEAD 填写 commit 和 artifacts；不要手打 SHA。若未设置 SWARMFORGE_ROLE，helper 会从 roles.tsv 和当前 worktree 推断角色。
  • 若你是带 specifier 的 pack 里的 master：工作就绪就排队 git_handoff。不要在窗格里求批准；操作者走 Attention。
  • 不要额外加 git 头（coverage、CRAP、证据）。需要证据时由 helper 来写。
  • git_handoff 只写：

type: git_handoff
to: <role>[,<role>...]
priority: NN
task: <短而稳定的任务名>

  • 做完入站任务后，无论改了什么，都要向链上下一角色发 git_handoff。只改格式、只改清单、只做 audit、只生成元数据，或其他非功能抖动，仍然要向前传。
  • 转发同一任务时保留收到的任务名。
  • master agent 用已有的 New Task / 看板卡片名当 task:。不要另起名字。
  • note 只写：

type: note
to: <role>[,<role>...]
priority: NN
message: <一行，最多 80 字符>

  • 若 swarm_handoff.sh 报校验错误：修好草稿再跑。
  • 发送成功后 helper 会删掉草稿。若要手动删过期草稿，用 rm <文件>，不要 rm -f。
  • 不要写长交接正文。送达载荷由 helper 生成。
  • 不要直接发 tmux 通知。
  • 不要手改、合并、暂存或提交交接运行时状态。
接收交接
  • 被通知时运行 ready_for_next.sh。未设置 SWARMFORGE_ROLE 时，helper 从 roles.tsv 和当前 worktree 推断。
  • ready_for_next.sh 按该角色配置的接收模式分派到 task 或 batch helper。对 git_handoff，它会合并入站 commit（merge_and_process.sh <sender> <commit>）。
  • 若 merge 或 ready 报冲突：解决每个冲突文件、git add、提交。冲突解决归你。不要发明新的 git merge。同一棵树上的并行卡片会冲突，这是预期。
  • 若打印 NO_TASK：停止等活。
  • 若打印 TASK: <path>：把打印出的 PAYLOAD 当任务。
  • 若打印 TASK_NAME: <name>：转发该任务时用这个稳定名。
  • 若打印 BATCH: <path>：把每条打印出的 BATCH_ITEM 按 helper 给出的顺序当作当前 batch 的一部分。
  • 只使用 helper 脚本打印出来的任务信息。
  • 若已经在做一项任务时又来了 tmux 唤醒：忽略它。
  • 任务或 batch 全部完成后运行 done_with_current.sh。
  • note 也是任务；读完或处理完 note 后，先 done_with_current.sh，再接下一个交接。
  • 若 done_with_current.sh 打印 MAIL_WAITING：作为新一轮再跑 ready_for_next.sh。不要把 done 的输出当成下一次 merge。
  • 若 done helper 打印 NO_TASK：停止等活。
  • 重启后运行 ready_for_next.sh 并按其输出行事。

工程规则

启动工具
  • 启动时，按项目语言，直接从列出的 github.com/unclebob/... 仓库取得所需 CRAP、变异、DRY 工具的最新版本，并准备好可运行。
  • 安装或构建前，把每个列出的仓库解析到当前能拿到的最新上游版本。
  • 只要当前环境能从 GitHub 全新安装/构建，就不要依赖过期缓存、vendor 或预装副本。
  • 语言工具表：
    • Go：go install；变异 github.com/unclebob/mutate4go，CRAP github.com/unclebob/crap4go，DRY github.com/unclebob/dry4go。
    • Clojure：Clojure CLI / deps.edn；变异 github.com/unclebob/clj-mutate，CRAP github.com/unclebob/crap4clj，DRY github.com/unclebob/dry4clj。
    • Java：Maven（mvn）；变异 github.com/unclebob/mutate4java，CRAP github.com/unclebob/crap4java，DRY github.com/unclebob/dry4java。
语言默认
  • Clojure 项目尽可能用 Babashka。
  • Clojure 或 Babashka 项目写 Speclj specs，不要用 clojure.test。
  • 用 swarm_tool.sh require speclj 安装 Speclj。缺失则 swarm_tool.sh ensure speclj。
  • 若 Speclj spec 文件有改动：运行 swarm_tool.sh require speclj-structure-check（缺失则 ensure），在跑测试前检查该 spec 文件。
  • Java 项目不要用 Maven 跑测试；构建专用测试 runner 再跑。
设计与可测性
  • 以小的、可评审的增量工作。
  • 选择能支撑当前行为、并为下一步留下清晰选项的最简设计。
  • 测试贴近正在改的行为。
  • 把可测模块与「环境上不适合自动测」的模块分开：打开 GUI、依赖外设、抛环境错误、打系统错误、或在自动测试里挂死的，都算不适合。尽量扩大可测代码，缩小不适合的边界。
  • 只有可测模块才参与会跑测试的工具：单元测试、验收测试、覆盖率、变异测试、CRAP、会调测试的 DRY、属性测试。
  • 属性测试与常规验证分开。除非该角色拥有属性测试验证，或用户明确要求，否则不要把属性测试标签放进常规单元覆盖、Gherkin 验收变异、语言变异、CRAP 或覆盖率命令。
验收管线
  • Gherkin 验收测试使用 github.com/unclebob/Acceptance-Pipeline-Specification。
  • APS 提供 gherkin-parser、ir-dry-checker、gherkin-mutator。用项目本地 helper 安装；不要搜 $HOME 或 find 二进制。
  • 工具启动时，每个需要的 APS 工具先 swarm_tool.sh require <tool>；缺失则精确运行 swarm_tool.sh ensure <tool>。
  • 双参数形式：
    • gherkin-parser <feature> ./tmp/<stem>.json
    • ir-dry-checker <ir> ./tmp/<stem>.dry.json
  • gherkin-parser、ir-dry-checker、gherkin-mutator 及相关 APS 命令优先用 Babashka 实现。
  • 仅当 Babashka APS 在当前项目环境不可用时，才用 Go 版 APS。
  • 项目自己的验收管线部件是：验收入口生成器、验收运行时、项目 step handler、runner 适配器、便利脚本。
  • Gherkin 验收变异 = 跑 gherkin-mutator 去变异 Gherkin 例子值。
  • Gherkin 验收变异必须定期报告进度，好让 agent 区分「正常很长」和「挂死」。
验证
  • 跑语言/构建/测试命令前，优先用本 worktree 内的项目本地缓存与配置路径。避免写到项目外、可能触发沙箱或权限问题的默认缓存。
  • 宪法工具一次只跑一个。不要并行跑 CRAP、DRY、覆盖率、语言变异、Gherkin 变异或 structure-check。
  • 有 worker 上限的工具必须用 --max-workers 4 或 --workers 4。
  • 函数变异相对源清单做差分。不要传 --mutate-all。
  • Gherkin 变异相对 feature 清单做差分（--level hard）。不要传 --level full。
  • 验收生成和验收测试顺序执行。
  • 避免整套语言测试命令与验收生成并行。
  • 项目若有本地验证命令，交接前跑相关的那条。
护栏
  • 不要发明项目本地的 CRAP / DRY / 变异 / 覆盖率代理。安装并运行宪法工具。不要把自制的 bb crap / bb coverage / bb mutation-count 当成那些工具。
  • 不要手改变异测试或 Gherkin 验收变异的清单；让获准的变异工具在正常运行中更新清单。
  • 除非任务需要，否则不要提交无关的本地改动或生成物。
  • 不熟悉的命令，先看本地 help 或项目文档再依赖它。

第三层：pack 只决定「几个人、排什么队」

Pack 角色链 什么时候用
two-pack coder → cleaner 小任务：要 TDD 和清理，不要 Gherkin / QA 专岗。
four-pack specifier → coder → refactorer → architect 中等项目：要规格和架构，但不把每个质量闸拆成独立 agent。
six-pack specifier → coder → cleaner → architect → hardender → QA 大项目：规格、清理、架构、加固、验收各有专人。

你可以这样记：角色数量跟质量闸数量对齐，不跟「模型越贵越好」对齐。 master agent 是 worktree 为 master 的那个角色：four/six 是 specifier，two-pack 是 coder。New Task 和聊天只跟这个人说话。

同一名字在不同 pack 里职责会变窄或变宽：two-pack 的 cleaner 几乎包办清理、架构和变异加固；six-pack 把这些拆给 cleaner、architect、hardender。先记「这条链上这一棒管什么」，不要假设全仓只有一种 cleaner。

角色链里每个人干什么

角色是工种。每个工种对应一份 roles/<name>.prompt，启动后只做自己 Owns 的事，Does Not Own 的工具不要碰。

本课是地图：下面只给工种一句话，不嵌角色 prompt 全文。 Owns / Handoff 条文按 pack 在后面课里嵌中文。0002（coder / cleaner）、0003（specifier / coder / refactorer / architect）、0004（六角色，含 hardender / QA）。pack 本地的 project.prompt / local-*.prompt 也在对应课里。

specifier · 规格员

把你的意图写成可测的外部行为：Gherkin 场景、验收标准、例子。问清歧义，不规定多余实现细节。four/six-pack 里它是 master；交出后你要在 Attention 里批准，它自己不在窗格里求批准。

coder · 实现员

按已批准规格做行为切片：TDD 写单元测试，再写刚好能过的产品代码。four/six 里还要接好验收管线、生成验收测试。不跑 CRAP / DRY / 变异测试。那些交给后面的清理或加固岗。

cleaner · 清理员

行为不变，把刚写的代码收拾干净。two-pack 里它还兼架构审查和变异加固，并批量吃 coder 的交接。six-pack 里它只管局部清理、覆盖率、CRAP≤6、DRY，以及数变异位点；不跑真正的变异测试。

refactorer · 重构员

只出现在 four-pack，职责接近 six-pack 的 cleaner：保行为、提覆盖、降 CRAP/DRY、必要时拆过大的文件。另加属性测试支架。不引入新功能，不跑变异测试。

architect · 架构员

管模块边界、依赖方向（高层规则不依赖 IO/UI）、信息隐藏。four-pack 里它是末棒，还要跑语言变异和软 Gherkin 变异。six-pack 里变异交给 hardender，它改完结构后交给下一棒。

hardender · 加固员

只在 six-pack。在架构审查之后做变异加固：语言变异、软 Gherkin 变异，再复查 CRAP/DRY。不管 specifier 写的端到端 QA 套件。

QA · 验收员

只在 six-pack。把 specifier 的 QA 步骤做成可执行脚本，从用户界面跑端到端，不走项目内部 API。末棒：通过后向其余所有角色发 git_handoff，卡片才进 Done。

课里还会碰到的词

词 先这样理解
质量闸 流水线上单独占一个角色的质量关注点：规格、实现、清理、架构、加固、验收。闸越多，pack 越大。
BDD / Gherkin BDD 先写可观察行为；Gherkin 是常用文件格式（Given / When / Then）。本仓库 four/six 还要求 APS（可解析、可变异例子值）。详细例子见术语表。
TDD 先写会失败、且能抓住错误实现的单元测试，再写刚好够过的产品代码。coder 的默认手法。
CRAP 通用指标：改这段代码有多危险 = 复杂度 × 缺测试。公式见术语表。清理岗要把相关代码降到 6 或以下（比 crap4j 常见的 30、crap4java 默认的 8 更严）。
DRY 这里主要指宪法指定的重复代码检测工具，不是口头上的「别复制」。减的是有意义的重复，不是硬合并。
变异测试 故意改程序（mutant），看测试会不会失败。抓不住的叫 survivor，加固岗要补测试或改设计去「杀死」它。
worktree 同一 git 仓库的另一份工作目录。每个角色一份，避免抢同一棵树。名为 master 的角色用主工作目录。
git_handoff 本项目自造的交接格式。四行头指向一次已提交状态；下游 helper 合并那个 commit。不要把它理解成聊天或 PR 描述。
Attention 仪表盘上等人的区域：批规格，或回答 agent 的澄清。不要用窗格聊天代替批准。
tmux 终端会话复用器。agent 实际跑在项目专用 tmux 里；仪表盘只是你看它们的窗户。

更短的回看版在 术语速查。

第四层：一次任务在仪表盘上怎么走

卡片跟着 git_handoff 走；Done 靠最后一棒广播给所有其他角色。

你点 New Task，卡片出现在 master 泳道。下游角色用同一个 task: 名字交接。有 specifier 的 pack，specifier 交出时人要在 Attention 里 Approve。最后一棒的 to: 必须是每一个其他角色，卡片才进 Done 井。

agent 不互发 tmux

它们写草稿，跑 swarm_handoff.sh。handoffd 把文件拷进对方 inbox，只发通用唤醒。

三种 helper

发送 swarm_handoff.sh，接下 ready_for_next.sh，做完 done_with_current.sh。角色是 task 还是 batch，由 conf 决定。

两种消息

git_handoff 指向已提交状态；note 是一行短消息。宪法默认：没有明确授权就不要发 note。

隔离靠 worktree

非 master 角色在 .worktrees/<name>。状态在 .swarmforge/，不要提交 handoff 运行时文件。

这一课学完，你至少该带走什么

1. 这是编排层

SwarmForge 管角色、worktree、交接和仪表盘。

2. 先抓两层

先分 main / pack，再分宪法 / 协议 / 脚本。宪法入口在 pack；三篇共享法在 main，agent 必须整目录读完。

3. 任务跟着交接走

卡片不是故事板装饰；它跟着合法的 git_handoff 和最后的全员广播移动。

4. 角色是工种

specifier 写规格，coder 实现，后面几棒分别清理、改结构、加固、验收；同名角色在不同 pack 里宽窄不同。
