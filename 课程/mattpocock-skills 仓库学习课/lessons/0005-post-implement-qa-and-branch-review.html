Lesson 0005

所有 ticket 做完后，整体怎么验收

你已经走完 wayfinder / grill-with-docs → to-spec → to-tickets → 一张张 implement。每张票收尾时似乎都做过 code review。真正缺的不是再发明一个 QA skill，而是看清：单票评审覆盖什么、整分支对照 spec 覆盖什么、哪些验收其实只能由你来关。

预计 12 分钟 目标：会做整分支收尾 速查：整分支验收速查

先抓一句最重要的纠偏

仓库里没有独立的 /qa 来做“全部 ticket 做完后的整体验收”。

主线写到 ship 时，收尾 skill 是 /code-review。文档里的推荐也写得很直白：单票评审和整分支评审都要，吃不准时就“每张票看一次，最后再对分支点做一次总评”。你直觉里那句“对当前分支所有提交做一次整体 review，看有没有跑偏 spec”，正好就是这条。

为什么你会觉得“应该有个 QA 流程”

因为 phase 名叫 QA

ask-matt 把一个 session 里的阶段说成“grilling、implementation、the QA”。这是阶段名，不是 slash command。到了实现和验收的边界，例子甚至是 /compact we're going to QA this area。

因为以前真的有 /qa

它已经被删掉了。旧 skill 做的是“你边用边报问题，agent 帮你把 bug 开成 issue”，不是“功能做完后闸门式验收”。所以它被吸收进了 /triage 和 /to-tickets。

因为每张票看起来已经 review 过

implement 的最后一拍确实是跑 /code-review 再 commit。于是很容易以为整条链路已经自带验收，不再需要人上场。

单票 review 覆盖什么，漏掉什么

层 它能证明什么 它证明不了什么
单票 tdd + 全量测试 这张票承诺的行为，在约定 seam 上是红绿过关的。 别的票拼上来之后，组合路径是否还成立。
单票 code-review 这一小段 diff 有没有违反仓库标准，有没有漏掉这张票的要求。 票与票之间的交互、整段功能有没有从 parent spec 跑偏。
同会话里的自评 作者 agent 记得自己刚写完的假设。 独立评审。文档原话是：同一上下文审自己，不是 review，是带着 slash command 的确认偏差。
ticket 上的验收框 拆票时写下了“怎样才算这张票完成”。 implement 不会勾这些框，也不会关票。frontier 要你自己往前推。

所以：单票 review 是必要的，但不是整分支验收。 文档把整分支总评的独特价值说成一件事：抓住那些“每张票单独看都过、拼在一起才露馅”的交互。

整分支验收实际怎么走

1. 人先把票关上

implement 停在 commit。关票、勾验收框是你的事。不关的话，to-tickets 的 frontier 看起来会一直堵着。

2. 新开干净 session

不要沿用最后一张票的实现窗口。phase boundary 上，自动评审的标准动作是丢给 subagent / 新窗口，让当前实现上下文不要污染评审。

3. 对分支点跑 /code-review

fixed point 用 main 或这个功能分支的起点。把 to-spec 那份 parent spec 的路径或 issue 明确喂进去，不要让它只靠某张子票去猜。

4. 两轴分开读，不要揉成一句

Spec 轴就是你要的“有没有跑偏”：缺了什么、多做了什么、看起来做了但做歪了。Standards 轴问的是拼完之后代码还像不像这个仓库该有的样子。两轴故意不合并，免得一轴过了把另一轴盖掉。

5. 你自己把 demo 走一遍

vertical slice 的设计就是：每张票落地时都该能单独演示。整分支收尾时，对照每张票的 acceptance criteria 和 spec 里的 user stories，用真实路径看一遍。agent 的 Spec 轴是假设，不是证据。

6. 发现了就当新工作，不要空转

code-review 没有“直到干净为止”的收敛保证。带着引用的发现再开票或小范围 implement；不要循环到它再也挑不出东西。

两件容易一起混掉的事

你想问的 该用什么 不该用什么
这支功能有没有按 spec 做成 对分支点的 /code-review Spec 轴 + 你自己走 demo 已删除的 /qa，或再对每张票重复 implement
我边点边发现新 bug / 新缺口 现在走 /triage 或直接拆成新 tickets 假装这还是同一张旧票的“验收步骤”
整个代码库都漂了，不只这一支 diff /improve-codebase-architecture /code-review。它只看一段 diff，不看全库。

还有一个连带事实：spec 在开始写代码后就会过期。to-spec 文档说它是当时的快照，真正该留下的是 CONTEXT.md 和 ADR。所以整分支评审对照的是“当时锁住的 spec”，不是一份会自动跟着实现改写的活文档。

3 分钟自测

1. 所有 ticket 都 implement 完以后，仓库里有没有专门的 /qa 做整分支验收？

2. 每张票 implement 时已经跑过 code-review，整分支再看一次主要是为了抓什么？

3. 整分支对照 spec 的评审，更应该放在哪种 session？

这一课结束时，你应该能说出的 4 句话

1. QA 是阶段，不是命令

旧 /qa 管的是报 bug 开 issue；整分支验收不靠它。

2. 单票 review 必要但不完整

它看不见票间交互，也不会替你关票、勾验收框。

3. 总评就是对分支点的 code-review

新鲜 session，fixed point 用 main，Spec 轴对着 parent spec。

4. 人还要走一遍真实路径

sub-agent 报告是假设；demo 和验收框才是你签字的那一层。
