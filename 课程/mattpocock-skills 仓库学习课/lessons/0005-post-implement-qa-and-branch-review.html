Lesson 0005

所有 ticket 做完后，整体怎么验收

你已经走完 wayfinder / grill-with-docs → to-spec → to-tickets → 一张张 implement。这一课把验收收成一件事：单票评审为什么不够、整分支 /code-review 到底在查什么、spec 有缺口时要不要新开，以及本地 .scratch 里要不要跑 /triage。

预计 16 分钟 目标：会读两轴并分流后续工作 速查：整分支验收速查

先抓一句最重要的纠偏

仓库里没有独立的 /qa 来做“全部 ticket 做完后的整体验收”。

主线写到 ship 时，收尾 skill 是 /code-review。文档里的推荐也写得很直白：单票评审和整分支评审都要，吃不准时就“每张票看一次，最后再对分支点做一次总评”。你直觉里那句“对当前分支所有提交做一次整体 review，看有没有跑偏 spec”，正好就是这条。

为什么你会觉得“应该有个 QA 流程”

因为 phase 名叫 QA

ask-matt 把一个 session 里的阶段说成“grilling、implementation、the QA”。这是阶段名，不是 slash command。到了实现和验收的边界，例子甚至是 /compact we're going to QA this area。

因为以前真的有 /qa

它已经被删掉了。旧 skill 做的是“你边用边报问题，agent 帮你把 bug 开成 issue”，不是“功能做完后闸门式验收”。所以它被吸收进了 /triage 和 /to-tickets。

因为每张票看起来已经 review 过

implement 的最后一拍确实是跑 /code-review 再 commit。于是很容易以为整条链路已经自带验收，不再需要人上场。

这一课里的 seam 是什么

seam 是你观察行为的那条公开边界：站在接口外面看它做什么，不伸手进模块里面。

测试住在 seam 上，不住在内部实现上。所以单票说“在约定 seam 上红绿过关”，指的不是“所有测试都绿了”，而是：事先说好从哪条公开边界验行为，并且只在那里验。

为什么验收会碰到这个词

to-spec 写正文前就要先跟你确认测试 seam；tdd 只在这些事先约定的 seam 上写测试；code-review 对照 spec 时，没约定却用上的 seam 会变成发现。三者绑在同一份 spec 上。

越高越好，越少越好

优先用已经存在的 seam，能站在更高处观察就不要往下拆。一次改动里，理想数量是一个。新开很多 seam，通常意味着测试开始贴实现。

它不是“模块边界”的同义词

仓库刻意不用 boundary 这个词，避免和 DDD 的 bounded context 搅在一起。seam 说的是：行为在哪被替换、被观察。更完整的深模块词汇在 codebase-design，这一课只需要验收用得上的这层。

单票 review 覆盖什么，漏掉什么

层 它能证明什么 它证明不了什么
单票 tdd + 全量测试 这张票承诺的行为，在约定 seam 上是红绿过关的。 别的票拼上来之后，组合路径是否还成立。
单票 code-review 这一小段 diff 有没有违反仓库标准，有没有漏掉这张票的要求。 票与票之间的交互、整段功能有没有从 parent spec 跑偏。
同会话里的自评 作者 agent 记得自己刚写完的假设。 独立评审。文档原话是：同一上下文审自己，不是 review，是带着 slash command 的确认偏差。
ticket 上的验收框 拆票时写下了“怎样才算这张票完成”。 implement 不会勾这些框，也不会关票。frontier 要你自己往前推。

所以：单票 review 是必要的，但不是整分支验收。 文档把整分支总评的独特价值说成一件事：抓住那些“每张票单独看都过、拼在一起才露馅”的交互。

整分支验收实际怎么走

1. 人先把票关上

implement 停在 commit。关票、勾验收框是你的事。不关的话，to-tickets 的 frontier 看起来会一直堵着。

2. 新开干净 session

不要沿用最后一张票的实现窗口。phase boundary 上，自动评审的标准动作是丢给 subagent / 新窗口，让当前实现上下文不要污染评审。

3. 对分支点跑 /code-review

fixed point 用 main 或这个功能分支的起点。把 to-spec 那份 parent spec 明确喂进去；本地就是 .scratch/<feature>/spec.md。

4. 两轴分开读，不要揉成一句

报告必须是 ## Standards 和 ## Spec 两块。一轴过了不能把另一轴盖掉。下一节把这两轴拆开讲。

5. 你自己把 demo 走一遍

vertical slice 的设计就是：每张票落地时都该能单独演示。agent 的 Spec 轴是假设，不是证据；spec 里根本没写的缺口，它也看不见。

6. 发现了就分流，不要空转

code-review 没有“直到干净为止”的收敛保证。带着引用的发现，按后面的分流表处理；不要循环到它再也挑不出东西。

code-review 跟传统人审不是同一件事

它重点查的是“做没做对的东西”，不是“这段代码里有没有空指针”。

你的直觉对了一半：Spec 轴确实是在问 agent 有没有按 spec 做成。但要校正一句——它查的是 spec 里锁住的行为、决策和 seam，不是“实现手法像不像你脑子里的写法”。to-spec 自己就禁止把文件路径和代码片段写进 spec。传统人审爱抓的 null、race、off-by-one，文档明确说那是 Claude Code 自带的 review，不是这个 skill。

Standards 轴 Spec 轴
问的问题 写得像不像这个仓库该有的样子？ 做的是不是 spec 要的那个东西？
对照什么 仓库自己的标准文档，外加一组 Fowler code smell 底线 originating spec / issue 的原文
会报什么 违反已写标准（可以是硬伤），以及 smell（永远是判断题） spec 要了但没做成、多做了（scope creep）、看起来做了但做歪了
每条发现必须带 标准文件里的那条规则，或 smell 名加 hunk spec 里被引用的那一行

两轴故意跑在互相看不见的 sub-agent 里，最后也不合并、不排名。代码可以“标准全过、东西做错”，也可以“东西做对、风格不像这个仓库”。揉成一个总分，就是过的那轴把没过的盖掉。

还有一个验收时特别容易漏的点：Spec 轴看不见 spec 里根本没写的需求。“缺了”的意思是 spec 要了、代码没有。你点 demo 时才发现“当初漏了登录过期”，这条不会作为 Spec 失败出现——因为它不在对照物里。

验收发现问题时，要不要新开 spec

默认答案是不要。spec 是当时的决策快照，不是活文档。to-spec 写得很清楚：一开工它就会过期；真正该留下的是 CONTEXT.md 和 ADR。目的地没变，就在同一份 spec 下面补工作。

你看到的 这意味着 接下来做什么
Spec 轴：要了但没做成 / 做成了但做歪了 spec 仍是对的，实现跑偏了 对着同一份 spec 再开一张票，或小范围 /implement。不要新开 spec。
Spec 轴：多做了（scope creep） agent 做了 spec 没要的东西 先问你自己：这是该删掉，还是你其实想要？想要就当成新决策，而不是“评审通过”。
人走 demo 才发现 spec 漏了、写得不够 对照物本身不完整。Spec 轴通常不会替你喊出来 目的地没变：缺的决策需要的话先 /grill-with-docs，再在同一个 .scratch/<feature>/issues/ 里补票。学到的长期判断写进 CONTEXT.md / ADR，不要去改那份已经开工的 spec 当活文档。
目的地变了，原来那份 spec 会让你吃惊 这是 pivot，不是修票 删掉没做完的 tickets，旧 spec 留着当快照。重新 grill，需要跨 session 再 /to-spec。文档原话：pivot 时删未完成的票、留着 spec。

判断句就一句：还是同一个 destination，就补票；destination 换了，才配得上新 spec。 漏掉一个验收条件、需求写得不够圆，通常都还是同一趟。

triage 是干嘛的？本地 .scratch 用得上吗

/triage 是外来工单的上坡入口，不是你这条主线的验收步骤。

它只处理不是你创建的原始报告：别人提的 bug、外部功能请求、突然扔进来的 PR。它走一套状态机（needs-triage → 核实 → 必要时 grill → 写成 agent brief 或关掉），然后并回主线的同一扇门：ready-for-agent。to-tickets 拆出来的票已经是 agent-ready，再跑一遍 triage 是浪费。

你本地看到的 .scratch/，就是这套技能的本地 markdown tracker，和 GitHub Issues 是二选一，不是两层。一份功能大概长这样：

  • .scratch/<feature>/spec.md — parent spec
  • .scratch/<feature>/issues/01-xxx.md — 一张票一个文件
  • 票上的 Status: 行，就是 triage 状态在本地的落点

所以：tracker 能跑 triage，不代表你这条工作流该跑。 文档自己也说了——如果 tracker 里的东西都来自你自己的规划，你会很少打开 /triage。它真正值钱的场景是开源仓库、团队往你这里扔原始 issue。本地独唱、票都是 to-tickets 写进 .scratch 的，验收时发现缺口，直接在同一个 issues/ 里补票，或先 grill 再补；不要把这些票再送去 triage。

只有一种本地情况它才开始有用：tracker 里突然多了一条还没被你规划过的原始备注——同事丢来的、用户反馈、你随手记下但完全没拆过的东西。那时 triage 的核实、去重、agent brief 才帮得上忙。

不要拿错工具

你想问的 该用什么 不该用什么
这支功能有没有按 spec 做成 对分支点的 /code-review Spec 轴 + 你自己走 demo 已删除的 /qa，或再对每张票重复 implement
实现做错，spec 仍对 同一份 spec 下补票 / 小范围 /implement 新开一份 spec
demo 时发现 spec 漏了，目的地没变 必要时 grill，然后在同一个 .scratch/<feature>/issues/ 补票 /triage，或把旧 spec 当活文档改来改去
目的地变了 删未完成的票，留旧 spec 当快照，重新 grill / to-spec 在旧票上硬修，假装还是同一趟
别人丢来的原始 bug / 请求 /triage（本地 .scratch 也能跑，但你要先真有一条外来 issue） 对 to-tickets 产出的票再 triage 一遍
整个代码库都漂了，不只这一支 diff /improve-codebase-architecture /code-review。它只看一段 diff。

3 分钟自测

1. 所有 ticket 都 implement 完以后，仓库里有没有专门的 /qa 做整分支验收？

2. 这一课里的 seam，指的是什么？

3. 这个 /code-review 的 Spec 轴，核心在问什么？

4. 验收时发现 spec 漏了一个需求，但功能目的地没变，默认怎么做？

5. 本地 .scratch 里那些由 to-tickets 拆出来的票，验收时要不要再跑 /triage？

这一课结束时，你应该能说出的 7 句话

1. QA 是阶段，不是命令

旧 /qa 管的是报 bug 开 issue；整分支验收不靠它。

2. 单票 review 必要但不完整

它看不见票间交互，也不会替你关票、勾验收框。

3. seam 是测和审共用的公开边界

站在接口外观察行为。spec 先约定它，tdd 只在那里测，review 会查有没有跑到没约定的地方。

4. 总评是两轴，不是传统人审

Spec 轴问对不对的东西，Standards 轴问像不像这个仓库。它不主抓空指针。

5. spec 看不见自己漏掉的需求

人走 demo 才补得上这块。Spec 轴只对照已经写下来的句子。

6. 目的地没变就补票

不要默认新开 spec。pivot 才删未完成的票、留旧快照、再 grill。

7. 本地 .scratch 很少需要 triage

它能跑，但只对外来原始工单有用。你自己拆的票已经 agent-ready。
