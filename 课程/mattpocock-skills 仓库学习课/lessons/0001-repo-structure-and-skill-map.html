先建立这个仓库的地图感

这节课先给 mattpocock-skills 画地图。你要看见目录结构、主要分桶、两条分类轴和主线怎么串，不把它读成一堆散落的 SKILL.md。

预计 12 分钟 目标：建立全局地图 回看资料：速查地图

先记住一句总判断

这个仓库不是“一个超级技能”，而是一套可组合的小技能系统。

所以你理解它的关键，不是逐字背每个 skill，而是先认出它用什么方式把 skills 组织起来：先分 bucket，再分调用方式，再放进一条或几条 flow 里。这个判断来自仓库总览和 `ask-matt` 的流程描述。

第一层：顶层结构在说什么

README.md 是总入口

先讲“为什么会有这套 skills”，再讲安装方式、项目哲学和技能总表。你第一次看项目时，这里负责建立全局感。

CLAUDE.md 是维护规则

它告诉你 bucket 怎么分、哪些 skill 算 promoted、以及 README、docs、插件 manifest 之间必须保持怎样的同步。

skills/ 才是主内容区

skill 都在这里，不是随便平铺，是分到 `engineering`、`productivity` 等五个桶里。

plugin.json 是发布视角

它不是教学文档，是最直接的“出货清单”：哪些 skill 真会进 Claude 插件，一眼就能看到。

第二层：先看 bucket，再看单个 skill

Bucket 你可以怎么理解它 当前读法
engineering 工程主线技能 和“从想法到交付”的流程最相关，优先看。
productivity 通用协作技能 像 `teach`、`handoff`、`wait-what` 这种跨场景能力在这里。
misc 保留区 知道它存在即可，不把它当主航道。
in-progress 公开试验区 适合观察新方向，但不当稳定接口。
deprecated 退役区 知道它被放弃了，比精读更重要。

这里最值钱的判断不是名字本身，是 promoted buckets 只有两个：`engineering` 和 `productivity`。这两个桶必须进顶层 README，也必须进插件 manifest；其他三个桶不能混进去。规则原文就在下面这份维护文件里；ask-matt 全文放到 0002，这一课只建立地图。

地图里的规则 · 分桶怎么写进仓库

CLAUDE.md（中文全量）

原文：CLAUDE.md · 本课要对照的就是：哪些桶算 promoted、README / 插件清单怎么同步、user-invoked 和 model-invoked 怎么标。

Skills 按 bucket 文件夹组织在 `skills/` 下：

- `engineering/` — 日常写代码的工作
- `productivity/` — 日常非代码工作流工具
- `misc/` — 留着但很少用，不晋升
- `in-progress/` — beta：故意公开，欢迎反馈，不打进插件
- `deprecated/` — 不再使用

`engineering/` 或 `productivity/` 里的每一个 skill（**promoted** buckets）都必须在顶层 `README.md` 有引用，并且在 `.claude-plugin/plugin.json` 的 `skills` 数组里有一条（Claude Code 插件正好只出货 promoted 这一套）。`misc/`、`in-progress/`、`deprecated/` 里的 skill 不得出现在这两处。

安装命令从 `.agents/install-block.md` 原样复制。`.claude-plugin/marketplace.json` 让本仓库成为自己的单插件 marketplace —— 这是安装块里说明的兜底，不是文档写的主路径。改完任一 manifest 后跑 `claude plugin validate . --strict`。为什么做 Claude 插件、暂时不做 Codex 插件，见 `.agents/adr/0002-ship-as-a-claude-code-plugin.md`。

顶层 `README.md` 里每一条 skill 都必须把 skill 名链到它的 `SKILL.md`。

每个 bucket 文件夹都有一份 `README.md`，列出该桶里每一个 skill 和一行描述，skill 名链到 `SKILL.md`。promoted buckets 的 `README.md` 和顶层 `README.md` 把条目分成 **User-invoked** 和 **Model-invoked**；非 promoted bucket 的 `README.md`（`misc/`、`in-progress/`）用扁平列表。

`engineering/` 和 `productivity/` 里的 skill 还有给人看的 docs 页，在 `docs/<bucket>/<skill-name>.md`（docs 树镜像这两个 bucket）。发布 URL 是 `https://aihero.dev/skills-<skill-name>`，与 bucket 无关 —— docs 路径只是仓库组织。当你在 `engineering/` 或 `productivity/` 里新增、改名或改行为时，按 `.agents/writing-docs.md` 创建或重同步 docs 页。完成的页面有四节 — **What it does**、**When to reach for it**、**Common questions**、**It's working if**；`writing-docs.md` 里有模板、节顺序、以及去哪找问题。非 promoted buckets（`misc/`、`in-progress/`、`deprecated/`）的 skill **没有** docs 页。

每一份 `SKILL.md` 要么是 user-invoked（`disable-model-invocation: true` 加上 `agents/openai.yaml` 里的 `policy.allow_implicit_invocation: false`，只有人能触发），要么是 model-invoked（模型或用户都能触发）。见 `.agents/invocation.md`。

`ask-matt` 是路由器：映射每一个用户能触达的 skill，以及它们怎么彼此关联。重同步 docs 页的同一条触发也适用于它：每当你新增、改名、删除、或改变一个用户可达 skill 在流程里的位置，就重读 `ask-matt` 的 `SKILL.md` 并更新它，让地图保持准确 —— 新 skill 从未被提到、或过时 skill 仍被路由到，就是在撒谎的路由器。

要把每一个 skill（重新）链到本机 harness 的 skill 目录（`~/.claude/skills`、`~/.agents/skills`），跑 `scripts/link-skills.sh`。每一项都是指向本仓库的 symlink，所以 `git pull` 会让已安装 skill 保持最新；增删改名之后再跑一次脚本。

第三层：再抓第二条分类轴

user-invoked

只有用户明确输入时才会走到。它们通常承担“编排流程”的职责，比如 `/ask-matt`、`/grill-with-docs`、`/teach`。

model-invoked

模型自己也可以在合适时机调用。它们更像可复用的底层 discipline，比如 `tdd`、`code-review`、`grilling`。

一个很实用的记忆法是：user-invoked 更像“入口和流程”，model-invoked 更像“方法与约束”。

第四层：用 ask-matt 把主线串起来

主线是：idea → grill-with-docs → to-spec → to-tickets → implement

`ask-matt` 最有价值的地方，是它不只是告诉你“仓库里有什么”，而是告诉你“这些 skill 在什么时候接力”。这就是为什么它像路由器，而不是单纯索引。

triage

当工作从外部 issue 涌进来，不是你自己发起的想法时，先 triage 再并回主线。

diagnosing-bugs

当问题是“出 bug 了”，先建立能可靠变红的反馈回路，再谈修复，而不是直接凭感觉改。

wayfinder

当工作大到一个 session 装不下时，先做决策地图，等 fog 被推开后再回到主线。
