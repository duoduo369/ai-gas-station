Lesson 0006

Issue tracker 是一份配置文档

这节课只讲 issue tracker 接线。skills 绑定的是 docs/agents/issue-tracker.md 里的流程；飞书、Jira、Linear 都能走同一条口。

目标：会选工作票放哪、共享板放哪 速查：tracker 接线速查

先抓一句关键纠偏

工程 skills 不绑定 GitHub。它们运行时去读仓库里的 tracker 文档，文档说写文件就写文件，说调 CLI 就调 CLI。

内置模板只有三份：GitHub（gh）、GitLab（glab）、本地 markdown（.scratch/）。Jira、Linear、Azure DevOps、Beads、飞书，全部是 setup 时选 Other，用一段散文把「怎么创建 / 读取 / 标状态 / 表达 blocking」写进同一份 issue-tracker.md。社区已经用 Linear CLI、Jira MCP、Gitea CLI 走过这条路。

你觉得 GitLab「乱」，撞上了两件不同的事

共享入口像主干

别人报的 bug、产品扔进来的需求、要公开讨论的议题，本来就该进团队看得见的板。GitLab Issues 适合干这个，/triage 也是为这类外来工单准备的。

工作票像分支

to-tickets 和 wayfinder 会拆出大量 agent 用的实现票、决策票。它们是开发过程产物。丢进同一个 GitLab 项目，就会出现你说的：一块板上混着很多 feature 的半成品。

仓库自己也承认这件事

开源维护者把 agent 规划票灌进公开 tracker，板会被填满，所以他们改用本地 markdown。文档同时警告反面：把这些文件提交进 git，容易「意外持久化」。你要的飞书文件夹，正好夹在这两极中间：持久，但不进代码库，也不进 GitLab 共享板。

和 git 的类比，精确到哪一步

Git 工作跟踪 别把它做成
私人分支上的 WIP .scratch/<feature>/，或飞书里按 feature 隔离的文档 / 多维表 把每张实现票都开成团队 GitLab Issue
只有要合的才进主干 MR / 提交说明里挂 一份 parent spec（外加必要时的父票链接） 把开发中的 blocking 图整板公开
别人的 PR 才是共享审查面 GitLab MR + 外来 issue 的 triage 让代码托管平台同时当所有人的草稿本

Jira 那套「提交末尾带一组 key」是 merge 时的指针。Skills 官方也写过常见拆分：Linear 管 issue 和规划，GitHub 只管代码和 PR。你可以把同一句换成：飞书（或 .scratch）管票，GitLab 只管代码和 MR。

setup 实际写什么

跑一次 /setup-matt-pocock-skills。它只问 tracker 放哪，然后生成：

  • docs/agents/issue-tracker.md — 创建、读取、评论、关票、以及 wayfinder 的 map / child / blocking / frontier / claim / resolve
  • 可选的 docs/agents/triage-labels.md — 五个角色名怎么映射
  • AGENTS.md / CLAUDE.md 里一段「Issue tracker」摘要，指向上面那份文档

之后 to-spec、to-tickets、wayfinder、triage、code-review 都按这份散文做事。换平台不用改任何 SKILL.md。GitHub 和本地 markdown 是二选一，不要叠两层各写一遍。

Section A — Issue tracker。

说明：这里的 “issue tracker” 是这个仓库的 issue 住在哪。to-tickets、triage、to-spec 这类 skill 会从那里读、往那里写 —— 它们需要知道该调用 gh issue create、在 .scratch/ 下写 markdown，还是遵循你描述的某种其他工作流。选你真正在这个仓库里跟踪工作的地方。

默认姿态：这些 skill 是为 GitHub 设计的。若 git remote 指向 GitHub，就提议那个。若 git remote 指向 GitLab（gitlab.com 或自建主机），就提议 GitLab。否则（或用户更想要），提供：

  • GitHub — issue 住在仓库的 GitHub Issues（用 gh CLI）
  • GitLab — issue 住在仓库的 GitLab Issues（用 glab CLI）
  • Local markdown — issue 作为文件住在本仓库 .scratch/<feature>/ 下（适合独唱项目或没有 remote 的仓库）
  • Other（Jira、Linear 等） — 请用户用一段话描述工作流；skill 会把它记成自由散文

把选择记进 docs/agents/issue-tracker.md。GitHub 和 GitLab 模板带一个 “PRs as a request surface” 开关，默认 关 —— 保持关掉，也不要主动提起；想把外部 PR 放进 triage 队列的用户可以以后在文件里把开关翻开。

然后用本 skill 文件夹里的种子模板写出 docs 文件：

  • issue-tracker-github.md — GitHub
  • issue-tracker-gitlab.md — GitLab
  • issue-tracker-local.md — 本地 markdown
  • triage-labels.md — 标签映射（仅当装了 triage）
  • domain.md — 领域文档消费规则 + 布局

对 “other” issue tracker，从用户的描述从头写 docs/agents/issue-tracker.md。

tracker 选项：

选项 issue 住在哪 需要
GitHub 仓库的 GitHub Issues gh CLI
GitLab 仓库的 GitLab Issues glab CLI
Local markdown 本仓库 .scratch/<feature>/ 下的文件 什么都不要 —— 完全没有 remote 也行
Other 你说的任何地方 你描述工作流的一段话

前三个作为模板打在 skill 里，开箱即用。本地 markdown 是一等公民选项，不是兜底：没有 remote 的独唱项目被完整支持。有一条 caveat 值得重复：如果你在用 GitHub，就不要再用本地 markdown。它们是替代方案，不是两层。

“Other” 也不是空壳。正是因为它，Jira、Linear、Azure DevOps 和 Beads 都能工作：你描述工作流，skill 把你的散文记进 docs/agents/issue-tracker.md，下游 skills 跟着散文走。社区已经这样做过 —— 一种经 MCP 的 Jira 变体、一个长得像 gh 的 Gitea CLI、一个手搓的本地仪表盘。

我必须用 GitHub 吗？

不必。GitHub、GitLab 和 .scratch/ 下的本地 markdown 都作为现成模板出货，其他任何东西走 “other” 路径。这是记录里重复最多的问题，大致是这些原话：“hard locked to github”、“can I use GitLab / Jira”、“what about Azure DevOps”。每次的答案都是：tracker 是一个 setup 答案，不是 skill 属性。

飞书能不能当 tracker：能，走 Other 路径

官方没有「issue-tracker-feishu.md」。飞书要工作，你得自己把 lark-cli 的调用约定写进 issue-tracker.md。CLI 是真的：飞书团队维护的 larksuite/cli 就是给人和 AI agent 用的，覆盖云文档、Drive 里的 markdown、多维表格、任务、知识库；项目工作项另有 meegle-cli。

按文件夹扔 markdown

最接近你现在的 .scratch：一个 feature 一个目录，spec 一篇，票一篇。Agent 靠列目录和读文件做 frontier。阻塞关系只能写在正文里的 Blocked by:，没有原生图，要人盯。

多维表格（Base）

更像「真 tracker」：状态列、关联列当 blocking、按视图筛出未阻塞未认领的 frontier。正文可以是记录字段，或链到一篇云文档。这比「一堆文件夹」更经得起 wayfinder。

飞书任务 / 项目

任务有子任务和评论，项目（Meegle）有工作项。只有团队已经在用它们当工单系统时才值得接；否则你是在给 agent 再教一套产品，收益不大。

一份能被 skills 执行的飞书接线，至少要写清这些动词，缺一项 agent 就会开始猜：

  1. publish：创建 spec / 票（含编号或 record id）
  2. fetch：按 id 读正文和评论
  3. 状态：ready-for-agent 等五个 triage 角色落在哪一列或哪段 YAML
  4. blocking：关联字段或正文约定；frontier 怎么查
  5. claim / resolve：认领和写完答案后改哪

针对你现状的默认建议

现在就可以用的

继续把 .scratch/<feature>/spec.md 和 issues/<NN>-<slug>.md 当工作票。这是一等公民模板，不需要 GitHub。不要把这些票再 triage 一遍，也不要同步进 GitLab。

想跨机器、给人看时

把 .scratch 的同一套目录约定搬到飞书 Drive / 知识库，或升级成一张按 feature 分表的 Base。合 MR 时只贴 spec 文档链接（外加表格里的父记录），不要贴十几张实现票。

先别做的

先别为了「有 CLI」就把所有票灌进飞书任务清单。共享清单会重新制造 GitLab 那种混杂。也先别写一个通用飞书 skill 去改 mattpocock-skills 源码；改的是你业务仓库里的 docs/agents/issue-tracker.md。

Issue tracker: 本地 Markdown

这个仓库的 issue 和 spec 作为 markdown 文件住在 .scratch/ 里。

约定
  • 一个功能一个目录：.scratch/<feature-slug>/
  • spec 是 .scratch/<feature-slug>/spec.md
  • 实现 issue 是一票一个文件，放在 .scratch/<feature-slug>/issues/<NN>-<slug>.md，从 01 起编号 —— 绝不要合成一个 tickets 文件
  • triage 状态记在每个 issue 文件顶部附近的 Status: 行（角色字符串见 triage-labels.md）
  • 评论和对话历史追加到文件底部的 ## Comments 标题下
当一个 skill 说 “publish to the issue tracker”

在 .scratch/<feature-slug>/ 下创建新文件（目录不存在就建）。

当一个 skill 说 “fetch the relevant ticket”

读被引用路径上的文件。用户通常会直接传入路径或 issue 编号。

Wayfinding operations

给 /wayfinder 用。地图 是一个文件，每张票一个 child 文件。

  • Map：.scratch/<effort>/map.md — Notes / Decisions-so-far / Fog 正文。
  • Child ticket：.scratch/<effort>/issues/NN-<slug>.md，从 01 起编号，问题写在正文里。Type: 行记录票类型（research/prototype/grilling/task）；Status: 行记录 claimed/resolved。
  • Blocking：顶部附近一行 Blocked by: NN, NN。一张票在它列出的每个文件都是 resolved 时 unblocked。
  • Frontier：扫描 .scratch/<effort>/issues/，找未关闭、未阻塞、未认领的文件；编号小的先赢。
  • Claim：先把 Status: claimed 写进去再开始任何工作。
  • Resolve：在 ## Answer 标题下追加答案，设 Status: resolved，然后给 map.md 里的 Decisions-so-far 追加一个 context pointer（gist + 链接）。

Issue tracker: GitLab

这个仓库的 issue 和 spec 住在 GitLab issues 里。所有操作使用 glab CLI。

约定
  • 创建 issue：glab issue create --title "..." --description "..."。多行描述用 heredoc。传 --description - 打开编辑器。
  • 读 issue：glab issue view <number> --comments。机器可读输出用 -F json。
  • 列出 issue：glab issue list -F json，配上合适的 --label 过滤。
  • 评论 issue：glab issue note <number> --message "..."。GitLab 把评论叫 “notes”。
  • 打上 / 去掉标签：glab issue update <number> --label "..." / --unlabel "..."。
  • 关闭：glab issue close <number>。glab issue close 不接受关闭评论，所以先用 glab issue note 发说明，再 close。
  • Merge requests：GitLab 把 PR 叫 “merge requests”。用 glab mr create、glab mr view、glab mr note 等 —— 和 gh pr ... 同形，把 pr 换成 mr。

仓库从 git remote -v 推断 —— 在 clone 里跑时 glab 会自动做这件事。

当一个 skill 说 “publish to the issue tracker”

创建一个 GitLab issue。

当一个 skill 说 “fetch the relevant ticket”

跑 glab issue view <number> --comments。

Wayfinding operations（节选）

给 /wayfinder 用。地图 是一条 issue，child issues 当票。

  • Map：一条打了 wayfinder:map 的 issue，装着 Notes / Decisions-so-far / Fog 正文。
  • Child ticket：描述顶部写 Part of #<map>，标签 wayfinder:<type>。
  • Blocking：GitLab 的 原生 blocking 链接。用 /blocked_by #<n> quick action。免费档没有原生 blocking 时，退回描述顶部的 Blocked by: #<n> 行。
  • Claim：glab issue update <n> --assignee @me —— session 的第一次写入。
  • Resolve：glab issue note 写下答案，然后 glab issue close，再给地图的 Decisions-so-far 追加 context pointer。

这一课结束时，你应该能说出的 5 句话

1. Tracker 是配置

唯一要改的是 docs/agents/issue-tracker.md。

2. 内置只有三份模板

GitHub、GitLab、本地 markdown。其余全是 Other。

3. 工作票不要进共享板

那是 GitLab 看起来乱的原因，也是开源仓库改用 .scratch 的原因。

4. 飞书能接，但要写动词

用官方 lark-cli。文件夹像远程 .scratch；Base 更像真 tracker。

5. 合码只挂 parent

MR 上放 spec 快照链接，不要放整板实现票。
