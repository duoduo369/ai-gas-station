Lesson 0002

把 ask-matt 读成一张路线图

上一课你已经知道这个仓库有地图感；这一课更进一步，专门学 `ask-matt` 怎么把一堆 skills 组织成“idea 到 ship”的主线，以及什么时候该从 triage、diagnosing-bugs、wayfinder 这些入口并回主线。

预计 10 分钟 目标：会读主流程 速查：ask-matt 流程速查

先抓最核心的一句

`ask-matt` 的价值，不是回答“仓库里有哪些 skill”，而是回答“在你当前这类问题里，下一步应该走哪条路”。

所以读它时，别把它当字典；把它当一个路由器。它把不同问题状态分流，再把它们并到合适的位置。

主线：从 idea 到 ship

阶段 为什么先做它 这一棒真正负责什么
grill-with-docs 想法还不够硬，直接写 spec 很容易把模糊假设写死。 通过 `grilling` + `domain-modeling` 把想法磨清楚，并留下 glossary / ADR 这类纸面痕迹。
prototype 有些问题只能靠“跑起来看”判断，而不是靠嘴说清。 回答一个设计问题，再把学习结果 handoff 回主线。
to-spec 当共识已足够，才进入“把它写成可交付说明”。 综合当前对话和代码库理解，产出 spec，并提前想清测试 seam。
to-tickets 多 session 构建如果不先拆 vertical slices，很容易上下文污染、粒度失控。 把工作拆成 tracer-bullet tickets，并显式写出 blocking edges。
implement 到了这一步，输入应该已经是相对稳定的 spec 或 tickets。 真正实施；内部驱动 `tdd`，结束前再跑 `code-review`。

这里最容易忽略的一点是：`implement` 不是单兵作战 skill，它默认站在前面几步已经做过的前提上。

为什么多 session 更推荐先 to-tickets

一个 ticket = 一个新鲜上下文窗口

`ask-matt` 明确建议每个 `implement` 尽量从新鲜上下文开始。这样每次实现只吃一小块、已经 agent-ready 的工作。

ticket 不是水平切片

`to-tickets` 要求的是 vertical slice：一个 ticket 应该打通 schema、API、UI、test 的完整窄路径，而不是“先全做后端，再全做前端”。

blocking edges 让顺序显式化

不是凭感觉排先后，而是把“谁阻塞谁”写出来。这样工作 frontier 才清楚。

三个上坡入口分别在解决什么前置问题

triage

你的问题不是“我有一个想法”，而是“外面来了一个 issue / PR，我要先判断它值不值得进入主流程”。

diagnosing-bugs

你的问题不是“我们做什么”，而是“到底什么坏了，如何先把 bug 稳定复现”。它的第一原则是 tight feedback loop。

wayfinder

你的问题不是“下一步实现哪块”，而是“这个目标太大、太雾，我连地图都还没有”。它先产出 decisions，不直接产出 deliverables。

一个很好用的判断法是：当你连“主线该从哪一段开始”都说不清时，通常你需要的不是更快执行，而是先走上坡入口。

独立技能：不在主线里，不等于不重要

真正独立

`research`、`prototype`、`to-questionnaire`、`wizard`、`wait-what`、`teach`、`writing-for-agents` 都能单独被拿出来解决特定卡点。

底层词汇层

`domain-modeling` 和 `codebase-design` 更像“底层语言包”。它们不是主线入口，但上层很多 skill 都靠它们统一说话方式。

phase boundary：什么时候不要急着 compact

`/compact` 是默认兜底，不是第一反应。

`PHASE-BOUNDARIES.md` 把五个选项排成顺序树，第一问永远是：还能不能继续留在当前 session 里？只有前面几项都不合适时，才落到 compact。

选项 你可以怎样理解它
Continue 如果下一阶段还需要当前推理过程做 primary source，那就尽量不断开。
/clear 如果当前上下文对下一步完全没价值，就直接清空，最便宜。
/handoff 只有在跨 harness、跨目录、交给别人、或中途分叉任务时才值得写。
Subagent 如果任务范围小、你又不需要在旁边盯着，那就外包给子代理。
/compact 相关上下文仍重要，但又必须切会话，这时才压缩总结。

3 分钟自测

1. 当一个想法还很模糊时，主线为什么不建议直接从 `to-spec` 开始？

2. 多轮次的大功能实现前，哪一步最能帮助你把每个 session 缩到可控范围？

3. 面对 phase boundary，五个选项里最先该排查的是哪一个？

这一课结束时，你应该能说出的 4 句话

1. ask-matt 是 router

它不是清单，而是“当前处境该走哪条流”的判断器。

2. implement 站在前置工作上

它不是从模糊想法直接开干，而是吃已经澄清、拆票后的输入。

3. on-ramp 解决前置状态

`triage`、`diagnosing-bugs`、`wayfinder` 分别处理不同类型的“还进不了主线”的情况。

4. compact 不是第一反应

phase boundary 的顺序树提醒你，先判断能不能继续，再谈压缩。
