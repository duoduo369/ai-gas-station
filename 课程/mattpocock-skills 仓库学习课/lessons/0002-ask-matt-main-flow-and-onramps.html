Lesson 0002

把 ask-matt 读成一张路线图

上一课先把仓库看平了。这一课直接读 ask-matt：它把一串 skills 串成 idea 到 ship 的主线，又从 triage、diagnosing-bugs、wayfinder 这些入口并回主线。

目标：会读主流程 速查：ask-matt 流程速查

先抓最核心的一句

`ask-matt` 回答的是：在你当前这类问题里，下一步应该走哪条路。

读它时把它当一个路由器。它把不同问题状态分流，再并到合适的位置。

Ask Matt

你记不住每一个 skill，所以来问。

一条 flow 是穿过这些 skills 的路径。大多数路径走一条 主线（main flow），两条 上坡入口（on-ramps） 并到这条主线上。其余的要么独立，要么是跑在底下的词汇层。

主线：idea → ship

大多数工作走的路线。你有一个想法，想把它做出来。

  1. /grill-with-docs — 用访谈把想法磨清楚。只要你在 工作目录里干活，就从这里起步：它是有状态的，学到的东西留在 CONTEXT.md 和 ADR 里。（没有工作目录？用 /grill-me —— 见独立技能。两者跑的是同一个 /grilling 原语；grill-with-docs 会留下纸面痕迹，所以只要有仓库可以留下痕迹，它就是更好的那个。）
  2. 分支 — 每一个问题都能在对话里解决吗？ 如果某个问题需要可运行的答案（状态、业务逻辑、必须看见的 UI），绕去原型，两边都用 /handoff 桥接（原型活在自己的目录里，这正是 /handoff 的用途 —— 见 Phase boundaries）：
    • /handoff 出去，然后对着那份文件开一个新 session，
    • /prototype 用一次性代码回答那个问题，
    • /handoff 把学到的东西带回来，并在原来的想法线程里引用它。
  3. 分支 — 这是一次跨多个 session 的构建吗？
    • 是 → /to-spec（把对话写成 spec），然后 /to-tickets 拆成 tracer-bullet tickets，每张票声明自己的 blocking edges。本地 tracker 上，那是 .scratch/<feature>/issues/ 下一票一个文件，按 blocker 优先、人手推进；真 tracker 上这些边变成原生 blocking 链接，所以 blockers 已完成的票谁都能抓 —— 每张票开一次 /implement，票与票之间 /clear 上下文。每张票是自洽的，所以上一张的上下文可以丢掉。
    • 否 → 就在这里、同一个上下文窗口里 /implement。

无论哪条，/implement 内部驱动 /tdd 来做每一张 issue —— 一次一块红绿切片 —— 收尾再跑 /code-review，对 diff 做两轴评审（Standards + Spec），然后才 commit。只想对一个具体行为做 test-first、不要完整 spec 时，单独用 /tdd；想对照某个固定点评审分支或 PR 时，单独用 /code-review。

上下文卫生

把第 1–3 步留在 同一个不间断的上下文窗口 —— 在 /to-tickets 之前不要 compact 或 clear —— 这样 grilling、spec 和 tickets 都建立在同一套思考上。之后每一次 /implement 都重新开始，只吃那张票。

这件事的上限是 smart zone：大约 15 万 tokens（前沿模型）之内，模型仍然推理得锐利。如果 session 在走到 /to-tickets 之前就接近这条线，不要硬撑着退化继续 —— 在最近的 phase boundary /compact，然后接着做（见 Phase boundaries）。

上坡入口

一种会生成工作、再并回主线的起始处境。

  • bug 和请求堆上来了 → /triage。它让 issue 走过 triage 角色，产出 agent-ready issues，之后由 /implement 捡走。

Triage 只处理 不是你创建的 issue —— bug 报告、外来功能请求、任何以原始形态到来的东西。/to-tickets 产出的票已经是 agent-ready，所以 不要再 triage 它们。

  • 有东西坏了 → /diagnosing-bugs。给难的那些：一眼看不穿的 bug、间歇 flake、两个已知好状态之间爬进来的回归。它拒绝空谈，直到有一条 紧反馈回路 —— 一条命令已经会在 这个 bug 上变红 —— 然后带着回归测试去修。事后分析若发现真正的问题是没有好 seam 能把 bug 锁住，就交接给 /improve-codebase-architecture。

  • 一大块有雾的努力 —— 绿地项目或巨大功能，一个 session 装不下 → /wayfinder，这里认知负担最重的一条流。从这里到目的地的路还看不见时，它在 issue tracker 上画出一张 共享地图，由 decision tickets 组成，一次解一张 —— 产出的是 决策，不是交付物 —— 直到雾被推开、路清楚了。/grill-with-docs 磨的是你能在一个 session 里 hold 住的想法；wayfinder 是给那个 hold 不住的 —— 它更慢、更密，所以只留给那种情况，绝不要用在已经界定清楚的功能上。

地图清楚之后，它交接，它不构建：在 /to-spec 并回主线，把地图上互相链接的决策压成可构建的计划，然后照常 /to-tickets 和 /implement。把地图直接 loop 进 /implement，等于跳过那次压缩、丢掉链接起来的细节 —— 只有这次努力后来证明真的很小，才直接 /implement。

代码库健康

不是功能工作 —— 是保养。

  • /improve-codebase-architecture — 有空就跑，让代码库继续适合 agent 操作。它会浮出 deepening opportunities；挑其中一个，就 生成一个想法，可以拿到主线的 /grill-with-docs。它是找出候选的勘察；/codebase-design（下面）才是你设计被选中那一个时用的工作台。
底下的词汇层

两份 model-invoked 参考，跑在 其他 skill 底下 —— 各自是那套词汇的单一事实源。当问题出在 用词 而不是流程时，直接去找它们；或者让上面的 skill 把它们拉进来。

  • /domain-modeling — 磨这个项目的 领域 语言：挑战一个模糊词，拆开一个身兼三职的词（"account"），把难逆转的决策写成 ADR。这是 /grill-with-docs 用来让 CONTEXT.md 保持干净 glossary 的主动纪律。
  • /codebase-design — 深模块词汇（module、interface、depth、seam、adapter、leverage、locality），用来设计模块的 形状：大量行为藏在干净 seam 上的小接口后面。/tdd 和 /improve-codebase-architecture 都说这套话。
Phase boundaries

一个 phase 是 session 里的一块工作 —— grilling、implementation、the QA。在两块之间的 边界 上你有五个选项，在这张地图里这是最模糊的决定：

  • Continue — 留在原地。零成本，零损失。
  • /clear — 清空窗口，这里的东西对下一步毫无用处时。
  • /handoff — 写一份可携带的 markdown。很窄：只用于 新 harness、新目录、同事，或 phase 中途 分叉旁支。它买到的是 portability。
  • Subagent — 把范围很紧的任务送到它自己的窗口，拿回一份报告。
  • /compact — 压缩这段上下文，用摘要去播种一个新 session。这是 默认项，在树的底部，不是第一伸手去够的。

读 PHASE-BOUNDARIES.md 看顺序树 —— 五个问题、每条分支背后的理由，以及为什么 primary-source 的代价让 Continue 必须先被排除。在边界上做决定；phase 中途，继续，或把剩下的拆给 subagent。

独立技能

完全离开主线。

  • /grill-me — 和 /grill-with-docs 一样不停访谈，但是 无状态：本地什么都不存，也不建 CONTEXT.md。在你 没有在工作目录里干活 时用它 —— 磨一个计划、一份设计、一篇文字，底下没有仓库。如果你在工作目录里，改用 /grill-with-docs：同一套访谈，会留下纸面痕迹，所以严格来说它更好。
  • /grilling — 访谈原语本身：rounds、frontier、事实是 agent 的活、决策是你的。/grill-me 和 /grill-with-docs 是两个具名入口；/triage、/wayfinder 和 /improve-codebase-architecture 内部都会跑它。只有当你想要没有外壳的访谈时，才直接去找它。
  • /resolving-merge-conflicts — 处理进行中的 merge 或 rebase，一块 hunk 一块 hunk 来，按追溯到双方 primary source 的意图解决，而不是挑行，然后做完这次操作。它从不跑 --abort。独立、不在任何 flow 上：你已经在冲突中间时才去找它。
  • /prototype — 一个小的、一次性程序，回答一个设计问题：这个状态模型感觉对不对，或这个 UI 该长什么样。Throwaway 约束的是代码怎么写，不是承诺销毁它：答案折进正式代码，原型本身作为 primary source 留在 prototype/<name> 分支上（离开 main），由实现 issue 指过去。它是主线第 2 步的绕路，但任何纸上很难拍板的设计问题都可以用。
  • /research — 把阅读苦力外包给 后台 agent：它对照 primary sources 调查一个问题，然后在仓库里留下一份带引用的 Markdown。它读的时候你继续干活。它产出的文件是拿 进 主线 /grill-with-docs 的东西 —— research 喂思考，不代替思考。
  • /to-questionnaire — 挡住你的东西不在你脑子里、也不在代码库里，而在 别人脑子里 时，给对方写一份问卷去填。它是 /grill-me 的反面：不是访谈你关于主题，而是访谈你关于 发送 —— 寄给谁、你要拿回什么 —— 并把问题对准那个缺口。收回来的材料给 /grill-with-docs 或 /to-spec。
  • /wizard — 只属于 人 的步骤：开通基础设施、配凭证或 CI secrets、点开不熟的第三方后台、跑一次性迁移或切流。它生成交互式 bash 脚本，打开每个 URL、捕获每个值、写进 .env 和 GitHub secrets —— 于是这套手续不再每次都要再向 agent 解释一遍。Model-invoked，所以 agent 撞上只有你过得去的墙时会自己伸手。如果 agent 自己就能做，它就该自己做；这是给真正需要人在环里的地方。
  • /wait-what — 上一条消息没打中时的纠正。在对话中途、在任何其他 skill 里面用，agent 会用你当时缺的上下文、用白话、用 CONTEXT.md 的词汇，把刚才那句话重新讲一遍。它是事后药；/grill-with-docs 是事前预防，因为早早就定下的共享语言才是不让行话冒出来的办法。
  • /teach — 跨多个 session 学一个概念，把当前目录当成有状态的工作区。
  • /writing-for-agents — 写给 agent 读的文档参考：skills、AGENTS.md、被指向的 docs。
前置条件

/setup-matt-pocock-skills — 第一次走工程 flow 之前跑，配置其他 skill 假定存在的 issue tracker、triage 标签和文档布局。自定义 issue tracker 也可以。

主线：从 idea 到 ship

阶段 为什么先做它 这一棒负责什么
grill-with-docs 想法还不够硬，直接写 spec 很容易把模糊假设写死。 通过 `grilling` + `domain-modeling` 把想法磨清楚，并留下 glossary / ADR 这类纸面痕迹。
prototype 有些问题只能靠"跑起来看"判断，靠嘴说不清。 回答一个设计问题，再把学习结果 handoff 回主线。
to-spec 当共识已足够，才进入"把它写成可交付说明"。 综合当前对话和代码库理解，产出 spec，并提前想清测试 seam。
to-tickets 多 session 构建如果不先拆 vertical slices，很容易上下文污染、粒度失控。 把工作拆成 tracer-bullet tickets，并显式写出 blocking edges。
implement 到了这一步，输入应该已经是相对稳定的 spec 或 tickets。 实施；内部驱动 `tdd`，结束前再跑 `code-review`。

`implement` 默认站在前面几步已经做过的前提上。它不是一个独立入口。

为什么多 session 更推荐先 to-tickets

一个 ticket = 一个新鲜上下文窗口

`ask-matt` 明确建议每个 `implement` 尽量从新鲜上下文开始。这样每次实现只吃一小块、已经 agent-ready 的工作。

ticket 要求垂直切片

`to-tickets` 要求 vertical slice：一个 ticket 打通 schema、API、UI、test 的完整窄路径。"先全做后端，再全做前端"违反这个原则。

blocking edges 让顺序显式化

把"谁阻塞谁"写出来，不凭感觉排先后。工作 frontier 才清楚。

三个上坡入口分别在解决什么前置问题

triage

外面来了一个 issue 或 PR，你先判断它值不值得进入主流程。

diagnosing-bugs

到底什么坏了，先把 bug 稳定复现。它的第一原则是 tight feedback loop。

wayfinder

这个目标太大、太雾，你连地图都还没有。它先产出 decisions，不直接产出 deliverables。

判断法：连"主线该从哪一段开始"都说不清时，先走上坡入口。

独立技能：主线之外的技能同样重要

独立可用

`research`、`prototype`、`to-questionnaire`、`wizard`、`wait-what`、`teach`、`writing-for-agents` 都能单独被拿出来解决特定卡点。

词汇层

`domain-modeling` 和 `codebase-design` 是词汇层。上层很多 skill 靠它们统一说话方式。

phase boundary：compact 是最后选项

`/compact` 是默认兜底、最后选项。

`PHASE-BOUNDARIES.md` 把五个选项排成顺序树。第一问：还能不能继续留在当前 session 里？前面几项都不合适时，才落到 compact。

选项 你可以怎样理解它
Continue 如果下一阶段还需要当前推理过程做 primary source，那就尽量不断开。
/clear 如果当前上下文对下一步完全没价值，就直接清空，最便宜。
/handoff 只有在跨 harness、跨目录、交给别人、或中途分叉任务时才值得写。
Subagent 如果任务范围小、你又不需要在旁边盯着，那就外包给子代理。
/compact 相关上下文仍重要，但又必须切会话，这时才压缩总结。

Phase boundaries

一个 phase 是 session 里的一块工作 —— grilling、implementation、the QA。这个定义故意模糊：当你觉得 "好，那块做完了"，一个 phase 就结束了。

phase boundary 是两个 phase 之间的空隙，也是这个决定唯一该出现的地方。phase 中途没有决定可做 —— 继续，或把剩下的工作拆给 subagent。在 phase 中途 compact，会让 agent 丢掉线索。

五个选项
选项 它做什么
Continue 留在这个 session。完全不切上下文。
/clear 清空上下文窗口，从零开始。
/handoff 写一份可携带的 markdown，用它在任何地方播种一个 session。
Subagent 把任务送到它自己的上下文窗口，拿回一份报告。
/compact 压缩这段上下文，用摘要去播种一个新 session。
这棵树

在边界上从上往下走。第一个 yes 赢。

1. 还能不能在这个 session 里继续？ 两件事会让答案变成 yes：下一 phase 需要这一 phase 当 primary source，或者你还剩足够的 smart zone（约 15 万 tokens）装得下下一 phase。Grilling → implementation 是标准的 yes：实现要的是推理原文，不是它的摘要。Continue 零成本、零损失，所以先排除它，再谈别的。

2. 这段上下文对接下来的事无关吗？ 这个 session 里的一切 —— 探索、决策、死胡同 —— 都可以丢掉吗？如果是，/clear。这是棋盘上最便宜的一步：不花时间，把整个窗口还你。/clear 也不是终点 —— 旧 session 仍可 resume。

这步走错的代价是单向的。清掉 相关 上下文，你就失去了构建背后的 为什么，再怎么回头读 diff 也找不回来。

3. 你需要交接吗？ /handoff 很窄。你只在这些时候需要它：

  • 换到 新 harness（Claude → Codex），
  • 换到 新目录 或仓库，
  • 把工作交给 同事，
  • 或在 phase 中途 发现一条旁支，又不想带偏正在做的事。

这份清单就是整条条款。/handoff 买到的是 portability —— 一份能带走的文件。没有东西在旅行，你就不需要它。

4. 这个任务能 AFK 做完吗？ 范围是否紧到你可以离开键盘、不用掌舵？那就丢给 subagent，本 session 不动。自动评审是标准案例：agent 读 diff 再报告，你不需要盯着。

5. 否则，/compact。 相关上下文、同一 harness、同一目录，而且你还得留在环里 —— 树落在这里，而且经常落在这里。给它一条指令（/compact we're going to QA this area），让摘要保住下一 phase 需要的东西。

/compact 是 默认项，不是第一伸手。它坐在底部，因为上面四个问题都更便宜或更精确。人们从这里起步的失败模式是：新 session 对摘要压扁过的决策自信地错。

Primary 与 secondary sources

除了 Continue，每一步都把 primary source 变成 secondary source —— 当时发生的 session，被一份摘要替换。这笔交易形状总是一样：

来源 信息 噪音 活动空间
Primary（Continue） 完整 很多 很少
Secondary（/compact、/handoff） 有损 更少 很多

这就是为什么问题 1 排第一。只有留下的成本高于它省下的，你才付这笔有损税。

这些是判断题

这些问题不是客观的 —— 每一问都有品味在里面，同一条边界两天可以走出两条路。价值在于 按顺序 问它们，在边界上问，而不是在工作中间问。

这一课结束时，你应该能说出的 4 句话

1. ask-matt 是 router

它判断当前处境该走哪条流，不是列出所有 skill。

2. implement 站在前置工作上

它吃已经澄清、拆票后的输入，不从模糊想法直接开干。

3. on-ramp 解决前置状态

`triage`、`diagnosing-bugs`、`wayfinder` 分别处理不同类型的"还进不了主线"的情况。

4. compact 不是第一反应

phase boundary 的顺序树提醒你，先判断能不能继续，再谈压缩。
