Issue tracker 是配置，不是平台

Skills 读 docs/agents/issue-tracker.md。内置 GitHub / GitLab / .scratch；飞书走 Other。工作票像分支，共享板像主干；合码只挂 parent spec。

三份模板 + Other

选项 票住哪 Agent 怎么动
GitHub 仓库 Issues gh
GitLab 仓库 Issues glab
Local markdown .scratch/<feature>/spec.md 与 issues/<NN>-<slug>.md 读写文件
Other 你描述的地方（Jira / Linear / 飞书 / Beads …） 你写进配置的 CLI、MCP 或 API

两层，不要叠成一层

共享入口

外来 bug、产品需求、/triage。可以继续用 GitLab Issue。

工作票

to-tickets / wayfinder。用 .scratch 或飞书按 feature 隔离。不要进共享看板。

合码指针

MR 或提交说明挂一份 spec 快照链接。不是把整板实现票公开。

飞书怎么选载体

载体 像什么 blocking / frontier
Drive / 知识库 markdown 目录 远程 .scratch 正文约定，靠扫目录
多维表格 Base 真 tracker 关联字段 + 视图筛选
任务 / Meegle 项目 团队已有工单系统 子任务；需团队已经在用

CLI：larksuite/cli。配置里必须写清 publish / fetch / 状态 / blocking / claim / resolve。

已知警告

  • GitHub 与本地 markdown 二选一，不要双写。
  • 本地文件提交进 git 容易意外持久化；公开 tracker 又会被 agent 票填满。
  • 没有原生 blocking 时，依赖图靠正文推断，要人校正。
  • 代码托管和 issue 可以拆开：GitLab 只管 MR，票走别处。
