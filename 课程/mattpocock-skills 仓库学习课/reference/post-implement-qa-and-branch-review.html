所有 ticket 做完后怎么验收

忘了主线收尾该做什么时，先抓一句：没有独立的整分支 /qa。单票 code-review 必要但不完整；整分支对照 spec 的动作，是新开干净 session，对分支点再跑一次 /code-review。

一句话区分

单票 implement 里的 review

看这一张票的小 diff：这张票有没有做成、有没有坏仓库标准。漏掉票与票的交互。

整分支 /code-review

fixed point 用 main 或功能起点，Spec 轴对着 parent spec。专门抓拼装后的跑偏和交互。

已删除的 /qa

旧技能是边用边报 bug、帮你开 issue，不是 ship 闸门。职责现在落在 /triage 和 /to-tickets。

你自己走的验收

关票、勾验收框、按 demo path 点一遍。这些 implement 都不会做。

推荐收尾顺序

步骤 做什么
关票 自己勾验收框、关掉已完成的 ticket。frontier 靠这个往前走。
换窗口 新开干净 session，不要沿用最后一张票的实现上下文。
总评 /code-review：fixed point = 分支点；spec = to-spec 那份 parent spec。
分轴读 Spec 轴看跑偏（缺、多、做错）；Standards 轴看拼完后的代码形状。不要揉成一个总分。
人走路径 对照每张票的 acceptance criteria 和 spec 的 user stories，真实点一遍。
停得住 有引用的发现再开新工作。不要把 review 循环到“再也挑不出东西”。

调用时要喂给它的两样东西

fixed point：通常是 main，比较命令是 git diff main...HEAD（三点，相对 merge-base）。

spec 源：优先显式给出 to-spec 产出的 parent spec / issue。不要只让它从某一张子票的 commit message 去猜整段功能。

不要拿错工具

情况 用
这支功能有没有按 spec 做成 整分支 /code-review + 人走 demo
点着点着发现新 bug /triage，或拆成新 tickets
不是这一支 diff，是全库都漂了 /improve-codebase-architecture
已经坏了，不知道为什么 /diagnosing-bugs
