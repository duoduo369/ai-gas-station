mattpocock-skills 速查地图

这是给回看用的压缩版资料：当你忘了这个仓库怎么分层、哪个 skill 处在主流程哪一段、哪些目录才算“对外主线”时，先翻这一页。

先抓四个判断轴

1. 这是 skills 仓库，不是应用仓库

顶层只有少量版本与插件脚本，重心在 skills/、说明文档、以及插件清单，而不是运行时业务代码。

2. 先看 promoted / non-promoted

engineering/ 和 productivity/ 是 promoted buckets；它们必须同时出现在顶层 README 和插件清单里。其他桶不能混进去。

3. 再看 user / model

skill 还沿着“谁能触发”这条轴再切一刀。user-invoked 负责编排流程，model-invoked 装的是可复用 discipline。

4. ask-matt 是路线图

如果 README 是总览，skills/engineering/ask-matt/SKILL.md 就是流程地图：主线、上坡入口、独立技能、底层词汇层都在这里。

顶层结构怎么读

位置 你该把它当成什么 为什么重要
README.md 总入口 讲安装方式、项目哲学、skill 总表，以及 user/model 两类 skill 的基本划分。
CLAUDE.md 仓库维护规则 解释 bucket 规则、promoted set、README 与插件 manifest 必须同步的约束。
skills/ 核心内容区 真正的 skill 文件都在这里，按 bucket 组织。
.claude-plugin/plugin.json 发布清单 列出插件会真正打包出去的 promoted skills。
docs/ 对外文档镜像 promoted buckets 下的 skill 还要同步一份 human-facing docs 页。

五个 bucket 的含义

Bucket 角色 是否进入顶层 README / 插件
engineering/ 日常代码工作主线 是
productivity/ 通用工作流主线 是
misc/ 保留但不主推 否
in-progress/ 公开 beta，欢迎反馈 否
deprecated/ 不再使用 否

主流程的最短记法

idea → grill-with-docs → to-spec → to-tickets → implement

这里的核心不是“一个神奇大招包打天下”，而是把对齐、拆分、实现、复盘拆成若干个小 skill 组合起来。`implement` 又会内部调用 `tdd` 和 `code-review`，所以真正的 discipline 是被层层下沉的。

上坡入口 1：triage

当工作源头不是你自己提出的想法，而是外来 issue、bug report、feature request 时，先把它们变成 agent-ready issues，再并回主流程。

上坡入口 2：diagnosing-bugs

当问题是“东西坏了”，就先建立能稳定变红的反馈回路，再谈修复，而不是直接猜。

巨大模糊项目：wayfinder

当工作大到单个 session 根本装不下时，先画 decision map；等地图清楚后，再回到 `to-spec` 开始进入可构建阶段。
