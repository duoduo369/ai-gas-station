Lesson 0003

spec 是入口还是工件

这一课只带走一句机制判断，并拆开两个都叫 SDD 的名字。读完不应得出「不要写 spec」，也不应把 Superpowers 执行环和业界 spec-first 脚手架听成同一个缩写。

预计 14 分钟 讨论课 · 无测验 回看：spec 与两个 SDD

先带走这句

被指摘的是把散文规格当入口、当银弹、当可以不看代码的借口；对齐之后的规格工件，再用测试 / 审查 / 变异去咬，这三套都还在用。结论不是『不要写 spec』。

上一课已经按轴填过：三套都在某个位置使用规格。骂声针对的是左半句；右半句仍在现场运转。把两半听成一句「spec 驱动已死」，会把 0002 的对照表读穿。

两个 SDD，必须拆开写

资料里随手写 SDD，常常在撞名。第一次出现就不能只留缩写。

业界 · Spec-Driven Development

先写（往往是 Markdown）规格，再让 agent 按规格生成代码。脚手架如 Spec Kit 族常被放在这一格。指摘也主要落在这里。

Superpowers · Subagent-Driven Development

计划获批之后，按 task 派子 agent 执行，再用审查咬住。它回答「谁去写、写完谁看」，不回答「散文规格能不能当银弹」。

指摘在骂哪一层

负命题

specs-to-code 是换皮的 vibe coding

Howardism 对 Matt 工作流的整理记下这条负命题：仔细写规格、交给 AI、代码不对就改规格、全程不看代码——试过，不行。代码才是战场；不碰代码的规格会退化成愿望清单；反馈环隔了一层，开发者的心智模型跟着腐烂。grilling 的纪律正好相反：规格在对齐下游，人对代码始终伸着手。

现场

Markdown 有损，agent 把 spec 当建议

Sibylline 写的是剧场：花大量 token 问精确需求，再有损摘要成 Markdown；实现时常见只跟上八到九成，缺什么要 QA 才知道。验证才是瓶颈。GitHub 讨论 #1784 是同一洞的现场版：生成大量文本，丢掉工作本质。

瀑布指控

先写完整 spec，等于假定实现教不会你任何东西

Opheleon 引用 Kent Beck：当前这波 spec-driven 工具把「实现不会反过来改规格」写进了前提。规格还会腐烂——过期的规格比没有更糟，因为它带着批准戳的错误信息。

这些指摘对准的是散文规格当入口 / 银弹 / 不看代码。它们没有证明「对齐之后不该留下一份规格工件」。

三套还在用 spec 的哪一层

把 0002 的「spec 位置」轴接到这句判断上，避免听成三套已经弃用规格。

方法 还在用的那一层 用什么去咬
Matt grilling 对齐之后，to-spec 把已经谈过的综合成规格。规格是目的地文档，不是出发令。 预先谈妥的测试缝、TDD、Standards / Spec 两轴审查。
Superpowers 批准闸之后才写设计 / spec，再拆 plan。规格仍是对齐的下游产物。 TDD、per-task 审查、整分支 final review。执行环是 Subagent-Driven，不是 Spec-Driven。
Bob 宪法约束角色；four / six-pack 的 Gherkin 是可执行规格，不是愿望清单。 生成的验收测试、变异硬化、QA 脚本。咬合力在能跑的东西上，不在更长的 Markdown。

这一课带走什么

结论不是「不要写 spec」。

以后读到 SDD，先问是 Spec-Driven 还是 Subagent-Driven。读到「spec 驱动被骂」，先问骂的是入口银弹，还是对齐之后那份还要用测试咬住的工件。三套方法都还站在后一种上。这门课到此收束：不推荐安装任何一套，也不把结论写成操作手册。
