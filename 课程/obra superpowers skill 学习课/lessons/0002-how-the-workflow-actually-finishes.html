Lesson 0002

功能做出来以后，工作流怎么收口

这节课补后半程。subagent-driven-development 不只是把功能丢给 subagent，executing-plans 也不是随手接上；review、final review 和 finish 才把这条线收住。

预计 20 分钟 目标：看懂后半程闭环 内嵌关键中文条文 回看资料：收口速查

先说你最熟悉、也最容易截断的版本

常见截断版心智模型：`brainstorming` 把设计讲清楚 → 自动长出 spec / plan → 叫 subagent 去实现 → 功能看起来能跑 → 人工点一点验收 → 结束。

Superpowers 的完整版心智模型：实现只是后半程的开头，不是结尾。完整闭环是“按任务推进实现 → 每任务 review → 全分支 final review → 进入 finish 菜单 → 由人决定 merge / PR / keep”。

为什么会误以为已经结束

因为“功能出现了”给人很强的完成感，尤其是 UI 或接口已经能跑的时候，容易把“能演示”误认成“工作流正式收口”。

真正漏掉的是哪些环节

最常漏掉的不是写代码本身，是 per-task review、whole-branch review，以及 finishing-a-development-branch 提供的正式收口菜单。

先把后半程主线摆成一张图

阶段 真正做的事 最容易被误解成什么
Step 3 之后 有了 plan，准备进入实现模式 “后面就是一直写代码”
SDD / executing-plans 按任务推进执行 “随便选一个让它干完”
Per-task review 每个任务都过一遍 spec + quality gate “做完所有任务再统一看看”
Whole-branch review 整条分支再做一次更宽的收尾检查 “前面都 review 过了，这步可以省”
finishing-a-development-branch 跑全量验证、给出整合菜单、按用户选择收口 “默认就应该自动 merge / 自动提 PR”

第一块重点：SDD 究竟是什么，不是什么

SDD 不是“把 feature 丢给 subagent”这么简单。

它是一整套控制方式：controller 留在上层做协调，每个任务派一个新的 implementer，任务后立刻 review，有问题进 fix loop，全部任务结束后还要做一次 whole-branch review，最后再进入 `finishing-a-development-branch`。只记住“里面用了 subagent”，等于没学到它的骨架。

Controller 不负责亲自补代码

SDD 里 coordinator 的职责是读 plan、派任务、看 report、派 reviewer、记录 ruling，而不是自己在主会话里东补一块西补一块。

粒度是 task，不是 feature

默认单位是“每个 task 派一个新实现者”，不是“一次派一个 agent 把整个 feature 做完”。这点决定了它为什么有 per-task review。

收口不是在 SDD 内部自动消失

SDD 的终点不是“代码都写完了”，而是“把整条分支推进到 final review clean，然后显式调用 `finishing-a-development-branch`”。

subagent-driven-development（中文节选）

原文：skills/subagent-driven-development/SKILL.md · 本课为什么要直接嵌：你要理解的不是“用了 subagent”，而是它如何把任务推进、review、fix loop 和 finish 接起来。

【Overview】
按实现计划执行时：
- 每个任务派一个新的 implementer subagent
- 任务完成后做 task review（先看 spec compliance，再看代码质量）
- 所有任务完成后，再做一次更宽的 whole-branch review

【Core principle】
Fresh subagent per task
+ task review（spec + quality）
+ broad final review
= high quality, fast iteration

【Continuous execution】
一旦开始跑 plan，就不要在任务之间反复停下来问“要不要继续”。
只在少数明确场景下停：不可逆操作、安全敏感操作、工作区外的副作用、或 plan 坏到往前走只能靠猜。

【The Process（压缩读法）】
1. setup：读 plan，建 ledger，检查前置冲突
2. 派 implementer
3. implementer 实现、测试、提交、自查
4. 派 task reviewer
5. review 干净 -> 任务完成
6. review 有问题 -> 进入 fix loop
7. 还有任务 -> 下一个任务
8. 没有任务了 -> broad final review
9. final review clean -> 用 finishing-a-development-branch 正式收口

【你在这一课该记住的关键句】
SDD 的骨架不是“subagent 帮你写代码”，而是“任务级 dispatch + 任务级 review + 分支级 final review + 显式 finish”。

executing-plans（中文节选）

原文：skills/executing-plans/SKILL.md · 本课为什么也要放进来：它能帮你看清楚 SDD 不是唯一执行模式，但它们最后都得接到同一个 finish skill。

【Overview】
读取 plan，先做批判性 review，再执行所有任务，完成后汇报。

【重要说明】
如果有 subagents，Superpowers 明确说：
更推荐用 subagent-driven-development。

【执行步骤】
Step 1：Load and Review Plan
- 先确保在隔离工作空间中
- 读 plan
- 批判性检查 plan
- 有问题先提出来；没问题再继续

Step 2：Execute Tasks
- 按 task 逐个执行
- 跟着 plan 里的步骤做
- 跑验证
- 标记完成

Step 3：Complete Development
- 所有任务执行并验证后
- 明确宣布要使用 finishing-a-development-branch
- 然后按那个 skill 的规则正式收口

【和 SDD 的差别，当前先抓一句】
SDD 更强调“任务级 dispatch + review loop”；
executing-plans 更像“单会话按 plan 顺序推进，遇阻就停下来 ask”。

第二块重点：Review 不是锦上添花，是 mandatory gate

如果你把 review 理解成“有空补一个”，后半程几乎一定会被你走短。

Superpowers 写得很明确：在 SDD 里，review 是每个 task 后的 gate；在更广义上，major feature 完成后和 merge 之前也都应该 request review。所以“功能有了”不能自动替代“review 过了”。

requesting-code-review（中文节选）

原文：skills/requesting-code-review/SKILL.md · 本课为什么要嵌：这张卡直接回答“什么时候 review 是必须的”。

【Core principle】
Review early, review often.

【Mandatory 什么时候必须 request review】
- 在 subagent-driven-development 里，每个 task 完成后
- 完成 major feature 之后
- merge 到 main 之前

【How to Request（当前先抓框架）】
1. 拿到 diff 的起止范围
2. 派 code reviewer subagent
3. 根据反馈处理：
   - Critical：立刻修
   - Important：继续前先修
   - Minor：可记录后续处理

【你在这一课该记住的点】
Review 在这里不是社交礼仪，也不是“别人顺手帮你看看”，
而是一个明确会阻止错误继续向后级联的控制点。

Per-task review

防止小错误滚进后续任务，把问题锁在局部任务范围内。

Whole-branch review

防止“每个任务单看都还行，但合在一起有缝”的问题漏过去。

第三块重点：Finish skill 负责把“实现完成”变成“正式收口”

真正的 finish 不是“我看着差不多，去 merge 吧”。

finishing-a-development-branch 最有价值的地方，是它把“收尾”从主观感觉，变成一套明确菜单和明确边界：先跑全量测试，再识别当前环境，再由用户选择 merge / PR / keep；只有用户明确要求 discard，才会走删除分支的路径。

finishing-a-development-branch（中文节选）

原文：skills/finishing-a-development-branch/SKILL.md · 本课为什么必须嵌：你提到的“功能有了，验收一下就完事”正是这张卡要纠正的地方。

【Core principle】
Verify tests -> Detect environment -> Present options -> Execute choice -> Clean up

【Step 1：先跑全量测试】
如果全量测试失败：
- 先停下
- 不能直接进入“怎么整合这份工作”的菜单

【Step 4：把菜单原样交给用户】
普通情况要给出 3 个选项：
1. 本地 merge 回 base branch
2. push 并创建 Pull Request
3. 保留当前分支，之后再处理

重点不是背菜单，而是：
整合决策是人类的，不是 agent 默认替人做主的。

【Discard 只在用户明确要求时才存在】
如果人明确要丢弃工作，必须先二次确认，并要求输入精确的 `discard`。
不是“差不多想删掉”就能算。

【Cleanup 也不是想删就删】
- 只有某些工作树是 Superpowers 自己创建并拥有 cleanup 权的
- 遇到未提交文件导致删除被拒绝时，不能擅自 `--force`
- 必须把风险展示给人，再让人选怎么处理

【你在这一课该抓住的点】
finish skill 的价值不是“给你一个 merge 命令”，
而是把收口动作变成显式菜单、显式确认、显式 cleanup ownership。

把整条后半程读成一句顺口的话

有了 plan 以后，不是“叫人实现完就结束”，而是：

选执行模式 -> 逐 task 实现 -> 每 task review -> 整分支 final review -> 进入 finish 菜单 -> 由人决定 merge / PR / keep。

如果你只把前半句走完，停在“功能看起来有了”，你得到的是一个可演示状态；把后半句也走完，才更接近一个正式收口状态。

可演示状态

功能跑起来了，表面体验通过，但 review 边界、整合方式、cleanup 责任都还没明确收束。

正式收口状态

验证通过、review 过关、分支级检查完成、用户明确做出整合选择，工作才算进入结尾。

4 分钟自测

这组题只检查一个目标：你有没有把“实现完成”和“工作流收口”分开。

1. 一个 feature 已经能点能跑，最准确的判断更接近哪一个？

2. 在 SDD 的正常节奏里，review 更像哪一种？

3. 如果平台支持 subagents，Superpowers 更推荐哪一种执行模式？

4. merge / PR / keep 这种整合决定，在 finish 阶段默认应该由谁来拍板？

5. cleanup 工作树时如果发现还有未提交文件，正确姿势更接近哪一个？

这一课学完，你至少该带走什么

1. “功能有了”不等于“工作流结束”

实现完成只是后半程的一部分，不是收口本身。

2. SDD 的核心是控制环，不只是 subagent

dispatch、review、fix loop、final review、finish 这些东西加在一起，才叫 SDD 的骨架。

3. Finish skill 把整合决策还给人

merge / PR / keep / discard 都有明确边界，不是 agent 自己顺手决定。

如果你已经把这节课消化住，下一步最顺的是这两个方向二选一：
