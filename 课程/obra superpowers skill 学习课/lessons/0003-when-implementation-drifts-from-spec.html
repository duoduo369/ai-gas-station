Lesson 0003

实现跑偏时，补任务、改计划，还是回到 spec

这节课专看实现跑偏。agent 跑过一轮、甚至报了 success 以后，reviewer 或人还会看到缺口。你得分清这是实现问题、plan 问题，还是 spec 变了。

预计 18 分钟 目标：学会跑偏分流 内嵌关键中文条文 回看资料：分流速查

先把最常见误区说破

最常见误区是：一发现跑偏，就本能地“再补一点代码”或者“干脆重开一份 spec”。

这两种反应都可能对，也都可能错。关键在先判断：错的是实现、是 plan，还是 spec 本身。分不清这三层，后面就很容易在错误层级上用力。

实现层错

spec 还是对的，plan 也大体对，只是实际代码没跟上，或者漏掉了某个 task 的交付。

plan 层错

spec 是对的，但任务拆分、顺序、接口传递、约束传递出了问题，导致实现层拿到的是残缺要求。

spec 层错

需求边界已经变了，或者你回头才发现原 spec 本来就写漏、写错、写得不够 authoritative。

先看总分流图

第一块重点：先认清谁是 authority

当实现和要求打架时，默认不是“谁最后说了 done 谁赢”，而是看 authority 顺序。

在 Superpowers 这套写法里，核心一句是：spec 是 binding authority，plan 是 spec 的 argument，implementation report 不是 authority，只是状态报告。 这句话已经决定了你发现跑偏后应该怎么分流。

subagent-driven-development（中文节选）

原文：skills/subagent-driven-development/SKILL.md · 本课为什么先读：它直接写了 spec、plan、execution 之间谁是上位 authority。

【关于 authority 的关键句】
如果 plan 里引用了 Spec，就要把 Spec 一起读。
因为 Spec 是 authority，plan 是它的 argument。

当 plan 内部互相冲突时：
- 不要直接跟着某一段字面跑
- 要拿 spec 作为绑定 authority 去裁决

【Pre-flight 与 rulings】
在执行前就应该扫描：
- task 之间是否互相矛盾
- task 是否违背 Global Constraints

如果发现冲突，不是沉默跳过，而是要明确做 ruling。

【Review loop 里的关键句】
如果 reviewer 报出的问题和 plan 文本冲突，
你不能因为“plan 是这么写的”就自动忽略 reviewer；
而是要回到 spec，看哪个才是 authoritative 的。

【你在这一课该记住的句子】
实现汇报“我做完了”不构成 authority。
spec 才是定义预期行为的上位文本。

verification-before-completion（中文节选）

原文：skills/verification-before-completion/SKILL.md · 本课为什么要嵌：它能直接帮你拆掉“agent 说 success 了，所以应该已经满足 spec”这个错觉。

【Core principle】
Evidence before claims, always.

【铁律】
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE

【针对需求达成的关键模式】
如果你要声称“requirements met”：
- 不是只看 tests passing
- 而是要重新对照 plan / requirements
- 一项一项核对
- 再报告 gaps 或 completion

【常见失败】
Agent reported "success"
≠ requirements met

【你在这一课该记住的点】
“它说做完了”只是信号，不是裁决。
裁决来自新鲜验证，以及对 spec / plan 的逐项回看。

第二块重点：三种情况，三种处理

情况 A：spec 对，plan 也基本对

这是最典型的“实现缺口”。此时不需要新开 spec。做法更像是：补 task、补实现、重跑 review，然后继续当前 feature 的收口流程。

情况 B：spec 对，但 plan 不够

比如 task 粒度拆坏了、顺序不对、关键约束没下传到 implementer。先修 plan 或补 plan 中缺的任务，再继续执行，不要先补代码。

情况 C：spec 本身不再 authoritative

如果你回头发现“真正想要的行为”已经变了，或原 spec 写漏了边界，那就不要继续在旧 spec 上缝缝补补。先修 spec，再刷新 plan，然后再恢复执行。

一句话判断：行为边界没变，不必新开 spec；行为边界变了，就要回到 spec 层。

“新开 spec”也不一定意味着非得另起一份全新文档。很多时候是修订当前 spec、补一段 addendum、或者重新确认 design section。但只要行为定义层变了，就不要假装它只是“实现层小修小补”。

第三块重点：review 指出缺口时，先验证，别立刻讨好式实现

review 发现缺口，不自动等于 reviewer 一定对，也不自动等于你应该立刻把所有意见全做了。

更稳的节奏是：先完整读完反馈，先判断它说的是 spec 缺口、plan 缺口，还是实现缺口；如果有不清楚的地方，先 ask；如果建议和当前 codebase reality 或 spec 冲突，先验证或 push back，再动手。

receiving-code-review（中文节选）

原文：skills/receiving-code-review/SKILL.md · 本课为什么要嵌：它正好回答“review 指出缺口后，到底是立刻改，还是先澄清 / 先验证”。

【Core principle】
Verify before implementing.
Ask before assuming.

【收到 review 的响应顺序】
1. READ：先完整读反馈
2. UNDERSTAND：用自己的话复述，或者先 ask
3. VERIFY：对照 codebase reality 检查
4. EVALUATE：对这个代码库来说技术上成立吗？
5. RESPOND：技术性确认，或有根据地 push back
6. IMPLEMENT：一项一项改，每项都验证

【处理不清楚的 feedback】
如果有任何条目不清楚：
- 先停
- 不要实现一半再回头问
- 先把不清楚的点问明白

【外部 reviewer 的建议】
在实现前要先检查：
- 对 THIS codebase 技术上是否正确
- 会不会破坏既有功能
- 当前实现是不是有上下文原因
- 是否与人类先前的设计决策冲突

【你在这一课该记住的点】
review 指出缺口，不是“表演性同意”的起点，
而是“重新验证自己是否站在对的 authority 层” 的起点。

最容易用错力气的 3 个现场

现场 1：agent 说 done，但人一看功能少一块

先不要重开 spec。先问：原 spec 里是不是本来就写了这块？如果写了，那大概率是实现缺口或 plan 缺口。

现场 2：review 说“这不满足要求”

先定位 reviewer 指的是哪一层要求。若 reviewer 说的要求不在 spec 里，那要讨论的是 spec 边界，不是马上讨好式补实现。

现场 3：人验收后改口，说真正想要的是另一种行为

这已经不是“补一个小洞”的级别，而是行为定义层发生变化。先修 spec，再谈后续任务怎么重排。

4 分钟自测

这组题只检查一个目标：你能不能分清“改实现”“改 plan”“回 spec”这三种动作。

1. 发现实现跑偏后，第一反应最该是什么？

2. reviewer 指出“少实现了一块”，最准确的默认判断更接近哪一个？

3. review 反馈里有两条你没完全看懂，正确姿势更接近哪一个？

4. 人验收后确认“真正想要的行为”已经变了，这时更合适的动作是什么？

这一课学完，你至少该带走什么

1. 先分层，再补洞

发现缺口后，第一件事不是修，是先判断错在实现、plan，还是 spec。

2. agent 报 done 不是 authority

它只是状态报告，不构成“已经满足 requirements”的裁决。

3. review 反馈要验证，不要表演性接单

有不清楚的先 ask，有冲突的先 verify，必要时 push back。

下一步怎么学最顺

这节课后，最自然的下一课就是 bug 流：

  1. 人验收时发现 bug，为什么不应该继续沿 feature 流硬补，而要切到 `systematic-debugging`。
  2. `systematic-debugging` 和 `verification-before-completion` 怎样接上，才能从“修了”走到“真的修好”。
