Lesson 0001

先把 Superpowers 看成一套工作系统

这节课先把 obra/superpowers 看成一套工作系统。你要看见仓库分层、基本工作流怎么推进、第一批该优先读的 skill 卡是谁。

预计 18 分钟 目标：建立总地图 内嵌关键中文条文 回看资料：速查页

先记住一句总判断

Superpowers 不是单个“神奇提示词”，而是一套把技能卡、流程门槛和 agent 行为约束缝在一起的方法系统。

这个判断能从仓库总入口 README.md 和 Codex 插件清单 .codex-plugin/plugin.json 一起看出来：一个在讲工作法和技能库，一个在讲这套东西怎样作为插件对外交付。

第一层：顶层结构在说什么

README.md 是总入口

这里负责建立大图景：它先讲这是什么，再讲怎么装、七步基本工作流是什么、仓库里有哪些核心 skill。第一轮阅读时，它比任何单个 skill 都更值得先看。

skills/ 是真正的主内容

真正可复用的方法卡都在这里，例如 using-superpowers、brainstorming、writing-plans。你后面精读，主要也是围着这里打转。

一圈 harness 目录是接线层

.codex-plugin/、.claude-plugin/、.cursor-plugin/、.devin-plugin/ 这些目录的存在提醒你：同一套工作法，需要分别接到不同 agent 环境里。

docs/ 与 tests/ 负责支撑

docs/ 里放额外说明、方案与平台文档，tests/ 负责插件基础设施验证。也就是说，这不是只靠 README 维持的仓库，而是有文档层和验证层一起支撑。

第二层：先抓这 4 份文件

文件 为什么先看它 你要带走什么
README.md 总图最完整 项目目标、安装入口、七步主线、技能总表。
using-superpowers/SKILL.md 方法门槛最强 为什么“先找 skill，再行动”被设成硬门槛。
brainstorming/SKILL.md 设计阶段总入口 任务怎样分成 spike / bounded / architectural 三条路。
writing-plans/SKILL.md 把设计变成执行 计划如何被拆成可验证、可交接的小步骤。

第二层补强：先把总门槛读成中文

按这门课的 playbook，这里不只告诉你“去看哪个文件”，还要把本课真正依赖的条文直接嵌进来。

0001 现在先把两张最该立刻看懂的规则卡放进课里：using-superpowers 负责“先检查 skill 再行动”，brainstorming 负责“创造性工作先设计、先审批、再实现”。writing-plans 的详细条文留给后续课，因为这一课只需要先知道它处在 Step 3 的位置。

using-superpowers（中文节选）

原文：skills/using-superpowers/SKILL.md · 本课为什么先读：它是整个仓库的总守门规则，不先理解它，很容易把 Superpowers 误读成“有空再用的技巧库”。

【核心规则】
在任何响应或动作之前——包括澄清问题、浏览代码库、检查文件——都必须先调用相关或被请求的 skill。
如果后来发现自己判断错了，那是下一步再修正的事；但“先检查 skill，再行动”这一步不能跳过。

在进入 plan mode 之前：如果还没有 brainstorm，就先调用 brainstorming。

然后要明确说出：
Using [skill] to [purpose]
并按该 skill 的要求完整执行。

【Skill 优先级】
如果多个 skill 同时适用，先处理流程型 skill，再处理实施型 skill。

- “我们来做 X” -> 先 superpowers:brainstorming，再进入实现 skill
- “修这个 bug” -> 先 superpowers:systematic-debugging，再进入领域 skill

【典型红旗】
- “这只是个简单问题” -> 错。问题也是任务，仍然要先做 skill check。
- “我先看看代码再说” -> 错。skill check 必须发生在看文件之前。
- “我记得这个 skill 的意思” -> 错。skill 会演化，要读当前版本。
- “这个 skill 有点大材小用” -> 错。觉得它像 overkill，往往正说明你在跳流程。

brainstorming（中文节选）

原文：skills/brainstorming/SKILL.md · 本课为什么先读：这张卡决定了“开始实现之前，人和 agent 到底应该完成什么对齐动作”。

【硬门槛】
在你把意图告诉人类并得到批准之前：
- 不要调用任何实现 skill
- 不要写代码
- 不要搭脚手架
- 不要采取任何实现动作

不管任务大小，批准门槛都在；变化的只是设计产物的轻重，而不是能不能跳过批准。

【三条路径】
Spike：
- 输出是答案，不是保留代码
- 用 2–3 句话说清你要验证什么、准备怎么试
- 得到点头后，再去廉价地探一遍

Bounded：
- 针对仓库里已经存在的流程做一个边界清晰的小改动
- 先问关键澄清问题
- 在聊天里给出短设计
- 明确拿到 yes 后，才能开始实现

Architectural：
- 新项目、新子系统，或会改变多个接口和边界的改动
- 走完整流程：澄清、方案比较、分段设计、写 spec、再交给 writing-plans

【最容易犯的反模式】
“这太简单了，不需要 approval”
-> 错。简单只意味着设计可以更短，不意味着可以绕过批准。

“先开始写，他们边看边批”
-> 错。设计可以很短，但 gate 是批准本身，不是文字长度。

第三层：README 里的七步主线怎么记

Step 1

brainstorming

先把模糊想法收束成可讨论的设计，而不是一上来就写代码。

Step 2

using-git-worktrees

设计过关后，把实现放到隔离工作空间里，避免直接把主工作区搅乱。

Step 3

writing-plans

把设计拆成一串短小、可验证的任务，而不是留在抽象口号层。

Step 4

subagent-driven-development / executing-plans

真正开始执行计划。这里决定的是“接下来由谁、用什么执行模式把任务往前推”，不是说到了 Step 4 就已经把代码全部写完。

Step 5

test-driven-development

这是 Step 4 里面每个实现任务都要遵守的写代码纪律：先写失败测试，再写最小实现，再看它变绿。

Step 6

requesting-code-review

这是 Step 4 里的任务间关卡。一个任务按 TDD 做完后，要先过 review，再继续下一个任务。

Step 7

finishing-a-development-branch

收尾不是“感觉差不多了”，而是验证、决定去向、再清理开发分支。

这一串顺序来自 README 的 Basic Workflow。最重要的不是记住所有名字，而是先意识到：Superpowers 想卖给你的不是单技，而是一条默认开发主线。

一个常见误读：很多人会把 Step 4、5、6 看成三段线性、互不重叠的执行命令。

更贴近实际的读法是：Step 4 是进入执行模式，Step 5 是这个执行模式里每个任务都要遵守的实现纪律，Step 6 是每个任务做完后的检查关卡。 所以真实节奏更像是：先走到 Step 4，然后在 Step 4 里面反复循环“按 TDD 实现一个任务 → review → 下一个任务”，全部任务结束后再走 Step 7。

第三层补强：执行环里的两张硬规则

如果你只记住七个名字，很容易以为自己已经懂了。

真正让你读懂 Step 4、5、6 关系的，不是 README 的那张总表，而是下面这两张更底层的条文：一张负责“任务怎么接力执行”，一张负责“任务里代码怎么落地”。

subagent-driven-development（中文节选）

原文：skills/subagent-driven-development/SKILL.md · 本课为什么先读：它把 Step 4 说得比 README 更具体，能直接解释为什么 Step 5 和 Step 6 像“套娃”而不是“下一章”。

【Overview】
按实现计划执行时，为每个任务分派一个新的 implementer subagent；
任务完成后做一次 task review（先看 spec 是否符合，再看代码质量）；
整条分支结束后，再做一次 broad whole-branch review。

【Core principle】
Fresh subagent per task
+ task review（spec + quality）
+ broad final review
= high quality, fast iteration

【每个任务的节奏】
1. 派一个实现者 subagent
2. 实现者实现、测试、提交、自查
3. 生成 review package，再派 task reviewer
4. review 过关 -> 任务完成
5. 还有任务 -> 回到下一个任务
6. 全部任务完成 -> broad final review
7. 最后进入 finishing-a-development-branch

【你现在该抓住的点】
Step 4 不是“写代码结束于此”，而是“从这里开始进入按任务推进的执行环”。
TDD 和 per-task review 都发生在这个执行环里面。

test-driven-development（中文节选）

原文：skills/test-driven-development/SKILL.md · 本课为什么先读：它不是“测试建议”，而是 Step 4 内每个实现任务都要守的硬规则。

【Overview】
先写测试。看它失败。再写最小代码让它通过。

核心原则：
如果你没有看过测试先失败，你就不知道这个测试是否真的能测出问题。

【铁律】
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST

如果你在测试之前就写了生产代码：
- 删掉
- 重新开始
- 不要把旧代码留作“参考”
- 不要一边补测试一边继续改那份代码

【Red-Green-Refactor】
RED
- 写一个失败测试

Verify RED
- 确认它是因为功能缺失而失败，不是因为拼写错误或测试本身坏了

GREEN
- 只写最小实现，让这个测试通过

Verify GREEN
- 确认测试通过，其他测试也还是绿的

REFACTOR
- 只在保持全绿的前提下清理命名、去重、抽 helper

【你现在该抓住的点】
Step 5 不是“做完 Step 4 后再补一轮测试”，而是 Step 4 里的写码方式本身。

第四层：第一批最值得抓住的 skill

using-superpowers

它像交通规则。先判断有没有适用 skill，再决定怎么做事情；连澄清问题之前都要先检查。

brainstorming

它像设计闸门。凡是创造性工作，先说清任务属于哪条路径，再拿到人类批准，不能边解释边开工。

writing-plans

它像施工图。真正的价值不是“有计划”，而是把计划写到没有上下文的执行者也能照着做。

test-driven-development

它像执行纪律。前面再会规划，如果实现阶段允许偷懒，整条流程就会重新退化成“拍脑袋编码”。

requesting-code-review

它像任务间闸门。不是所有任务全做完后才第一次 review，而是一个任务做完就该拉一次检查，避免错误滚到后面放大。

这一课学完，你至少该带走什么

1. 先认系统，不先认单卡

Superpowers 的重点是技能之间的接力关系，而不是某张单独 skill 的口号。

2. README 是主线图

它最值钱的地方不是安装说明，而是那条七步主线和对技能系统的总体 framing。

3. using-superpowers 是总门槛

不理解这张卡，就很容易把整个仓库误读成“可选技巧集合”，而不是强约束流程。

4. Step 4/5/6 是一段套娃关系

Step 4 是执行模式，Step 5 是任务内 TDD，Step 6 是任务间 review，不是三段彼此独立的流水线。

5. 总门槛值得在课里直接看条文

像 `using-superpowers`、`brainstorming`、`test-driven-development` 这种规则，如果只写“去看原文”而不把中文放进课里，你第一次学时很容易只记住名字，没记住门槛。
