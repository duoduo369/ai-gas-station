验收 bug 流与 worktree 位置速查

这页只回答最后两个现实问题：人验收发现 bug 时怎么切到 debug 流，以及 worktree 到底位于整条工作流的哪一层。

总判断

预期变了：回 spec 分流。

预期没变但东西坏了：切 systematic-debugging，修完后再走 verification-before-completion。

总图

验收 bug 的最短顺序

阶段 你该怎么记
先判断边界 预期变了没有？变了就回 0003，不变才进 debug。
systematic-debugging 先查 root cause，不准直接猜 fix。
失败用例 用最小失败测试锁定原始症状。
单一修复 一次只改根因，不顺手大翻修。
verification-before-completion 拿 fresh evidence 证明原始症状真没了。
finish 验证过后，才回到 branch finish 正式收口。

worktree 最短判断

  1. 先检测是不是已经在隔离工作空间里。
  2. 已经隔离好了，就不要再建一个新的 worktree。
  3. 如果平台有 native worktree 工具，优先用它，不要绕开 harness 手搓 git。
  4. 只有没有 native tool 时，才用 git worktree fallback。
  5. 进入工作空间后先做 baseline setup / tests，别让后续失败来源变模糊。

要看中文条文，回 0004 的这四处

  1. 0004 · 发现 bug 时先切线
  2. 0004 · systematic-debugging 不要求先有 spec
  3. 0004 · 修完以后要 fresh verification
  4. 0004 · worktree 是环境层
