Lesson 0001

腾讯 WorkBuddy skill 的结构，和常见 skill 结构有什么区别

这节先不写卡，先拆骨架。你要先看清 WorkBuddy 到底把什么写死了，再看像 writing-for-agents 这样的 skill 能帮你改哪一层，最后再把 OpenAI Skills 和 Claude Code Skills 拉进来对照。

目标：分清结构层和写法层 回看：结构速查

先记住这一句

WorkBuddy、OpenAI、Claude 都有 skill，但它们不在同一层发力。WorkBuddy 先管平台包结构，OpenAI 先管 API 挂载，Claude Code 先管本地开发环境里的按需流程扩展。像 writing-for-agents 这样的 skill 则根本不是平台格式，它们是帮你生成或改写 skill 正文的方法层工具。

如果你把这几样东西混成一团，最常见的后果就是：一会儿把长期规则误写进 skill，一会儿把补充知识硬塞进正文，一会儿又以为“多几个子目录”就是所谓行业标准。

先分层，再看差异

先看这张图。上面一层是写法层，下面一层才是平台实现。这个顺序很关键，因为你之后真要写 WorkBuddy skill 时，正文怎么写稳，可以借像 writing-for-agents 这样的 skill；而这个 skill 包最后要提交成什么形状，才是 WorkBuddy 文档管的事。

WorkBuddy 官方文档真正写死了什么

WorkBuddy 这页文档给你的，不是一套抽象理念，而是很具体的骨架：SKILL.md 在中间，frontmatter 要有固定字段，旁边还有三类子资源目录。你先把这套骨架看成“平台包结构”，后面很多判断才不容易跑偏。

别漏掉最后的发布形态： WorkBuddy skill 不是你本地目录摆好就结束了。开放平台文档明确提到，创建技能时会提交 zip 包；如果平台解析失败，就回到这套基础结构和子资源目录排查。也就是说，你最终交付的是一个按约定组织好的 skill 包，再打成 zip 上传到平台。

部件 WorkBuddy 文档怎么说 你该怎么理解
Frontmatter 至少把 description、description_zh、description_en、version、author 写出来 平台把“触发词 + 双语简介 + 作者版本”都当成结构的一部分
references/ 放补充知识文档，正文里通过 @references/... 引用 协议、字段、示例数据、最佳实践别都塞在正文里
scripts/ 放执行中要调用的脚本 真的有运行时逻辑时再放脚本，不要把模板也伪装成脚本
templates/ 放可复用模板脚本或配置文件 它是骨架，不是运行逻辑

对着原文看：WorkBuddy 这页最值得你盯住哪里

这节课不是全文精读 WorkBuddy 文档，所以我只把真正会影响你以后写卡的部分压进来：frontmatter 字段和三类子目录。它们决定的是结构边界，不是风格。

WorkBuddy 技能文档：frontmatter 与子目录

原文：WorkBuddy 开放平台 · 技能。这段够你判断最小骨架，不必把整页都背下来。

展开中文拆解 收起中文拆解 
---
name: your-skill
description: 写清用途和触发词
description_zh: 简短中文介绍
description_en: Short English description
version: 1.0.0
author: your-name
---

Frontmatter 字段

字段 必填 作用
name 否 技能标识。
description 是 写清用途和触发词。
description_zh 是 简短中文介绍。
description_en 是 简短英文介绍。
allowed-tools 否 工具白名单。
version 是 版本号。
disable-model-invocation 否 true 时 AI 不自动触发，只能手动调。
user-invocable 否 false 时只给 AI 内部使用。
author 是 合作方名称。

三类子目录

  • references/：补充知识文档，适合字段说明、协议、示例数据、最佳实践。
  • scripts/：执行中真正要调用的脚本，适合外部 API、批量处理、特定运行时逻辑。
  • templates/：可复用模板，适合脚手架、报告模版、标准化流程片段。

像 writing-for-agents 这样的 skill 帮你改的，不是目录，是写法

如果 WorkBuddy 这页回答的是“这包文件要长什么样”，那像 writing-for-agents 这样的 skill 回答的是“你写进 SKILL.md 的那些字，怎样才更稳”。它们一直在做两件事：减少始终加载的上下文成本，以及减少 agent 在执行时的分心和漂移。

Context pointer

description 不是简介那么简单，它是一个指针。它决定模型什么时候会去读这张卡，触发不触发，靠的是指针措辞，不是正文质量。

两种负担

一类是上下文负担：永远挂在窗口里的文字会持续耗 token。另一类是认知负担：人要记住有哪些卡、什么时候该叫它们。

信息层级

每次都要执行的步骤留在正文。只在部分分支才会碰到的知识，下沉到外部 reference。

调用方式也是结构判断

自动触发不是默认更高级。只有模型必须自己发现、或别的 skill 必须能 reach 到它时，自动触发才值得付上下文成本。

把用到的 skill 直接压进来

你要求这门课把 writing-for-agents 加厚进去，所以这里不只留外链，而是把这节课真正用到的两块正文压成静态 HTML：一块讲 description、分层和减负，一块讲 skill 到底该自动触发还是手动调用。

writing-for-agents：正文写法

原文：writing-for-agents · SKILL.md

展开中文正文 收起中文正文 
---
name: writing-for-agents
description: Writing documents for agents. Use when creating or editing skills, or modifying AGENTS.md or CLAUDE.md.
---

1. description 是指针，不是介绍词

一张卡能不能被模型可靠地 reach 到，先看 description 说得准不准。指针的措辞应该把触发分支写在前面，而不是先写身份介绍。

2. 永远挂在窗口里的字最贵

始终加载的 description、AGENTS 行、CLAUDE 规则都在持续占上下文。只有需要每次都看的东西，才值得留在这一层。

3. 把步骤和参考材料拆开

正文里放顺序动作。只在部分分支才需要、而且可以按需查阅的事实、定义、规则，下沉成 reference 文件。

4. completion criteria 要清楚

每一步最好都有能判断“做完没做完”的边界。边界模糊，模型就容易为了赶下一步而过早结束。

5. leading words 要真能挂住行为

如果一个词能稳定唤起同一种执行方式，它就值钱。反过来，只是“更认真一点”这类默认就会做的空话，通常是 no-op。

SKILL-MECHANICS：自动触发还是手动调用

原文：SKILL-MECHANICS.md

展开中文正文 收起中文正文

1. 自动触发，换来的是发现能力

如果模型必须自己发现这张卡，或者别的卡必须能 reach 到它，那就保留 description，让它留在上下文里。

2. 手动调用，换来的是零上下文税

如果这张卡只会由人显式叫起，就把它做成手动调用。这样模型平时不用一直背着它。

3. 共享 reference 不一定要做成另一张 skill

如果两张手动卡都需要同一份知识，最好的落点往往是普通 reference 文件，而不是再造一张无法自动 reach 的 skill。

4. router skill 解决的是“人记不住那么多卡”

卡很多、而且大多需要手动调用时，router skill 可以替人做索引。它不能代替触发，但能降低认知负担。

把三家放在一张表里，你就不容易再混

问题 WorkBuddy OpenAI Skills Claude Code Skills
skill 主单位是什么 一包以 SKILL.md 为中心的文件，旁边点名了三类子目录 一个版本化文件包，SKILL.md 是 manifest 本地目录里的 .claude/skills/<name>/SKILL.md
模型先看到什么 frontmatter，尤其三段 description name、description、path 会进 prompt 上下文 skill 名和描述会进技能列表，Claude 用它决定是否自动加载
支持文件怎么组织 文档直接命名 references / scripts / templates 文件包里可以放任意文件，没有固定目录名 skill 目录里也能放 supporting files，还支持动态上下文注入
手动 / 自动调用怎么管 frontmatter 有 disable-model-invocation 与 user-invocable 可以明确提示“use the X skill”，平台也会根据 metadata 决定是否调用 既支持自动加载，也支持 /skill-name 手动调；还能在设置里改可见性
skill 之外的长期规则放哪 这页文档没展开 更偏工具环境挂载，没有单独强调长期规则文件 长期规则放 CLAUDE.md，需要独立上下文的 worker 另走 subagents

你会发现，WorkBuddy 和 OpenAI 在“skill 是一包文件”这件事上更接近，Claude Code 则更强调“skill 是本地开发工作流的一种扩展点”。所以你如果拿 Claude 的 CLAUDE.md 去对比 WorkBuddy 的 SKILL.md，本来就不是一层东西。

如果你要写第一张 WorkBuddy skill，writing-for-agents 会怎么落地

1

先写 description，不要先写身份介绍

把触发分支写在最前面，让模型知道什么情况下该 reach 这张卡。WorkBuddy 既然还要求中英双语，那中文和英文最好都保持同一触发边界。

2

正文只留每次都要执行的动作

比如“先读什么，再做什么，做到什么算完成”。如果一大段知识只在部分分支才用得上，就不要一直压在正文里。

3

把事实和运行时逻辑拆开

字段定义、协议、最佳实践进 references/。真正需要执行的脚本逻辑再进 scripts/。别把两类东西混在一张卡里。

4

只在需要时才自动触发

如果这张卡就是手工工具，把 disable-model-invocation: true 打开，反而更省上下文税。自动触发不是默认更高级，而是更贵。

5

模板最后再放

只有当你真的有可复用骨架时，才建 templates/。没有就别为了目录完整而预建空壳。

这一课学完，你该带走什么

1. WorkBuddy 先定包结构

它最有辨识度的地方，是 frontmatter 的固定字段、references / scripts / templates 这三类目录，以及最后要把整包内容打成 zip 提交到开放平台。

2. writing-for-agents 定写法

它帮你判断 description 怎么触发、正文和 reference 怎么分层，不负责平台目录长什么样。

3. OpenAI 和 Claude 不是同一参考物

一个偏 API 挂载，一个偏本地开发环境扩展。拿它们对照 WorkBuddy 时，要先对齐比较层。

4. 自动触发不是默认更好

会不会自动触发，本质上是上下文预算和发现能力的交换。
