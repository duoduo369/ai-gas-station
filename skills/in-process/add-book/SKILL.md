# add-book

在本仓库里为一本技术书创建 `书籍/<书名>.md`，并同步更新书籍目录索引。
这里的“添加书籍”“创建书籍”“新建书籍笔记”默认都算要新建正文；只有用户明确说只改索引时，才停在索引条目。
当前版本先只服务技术书，不主动泛化到其他书类。
这条 skill 是技术书 `书籍笔记` 的唯一事实源；其他路由文档只负责把人和 agent 带到这里，不再并行维护另一套正文规则。

## Before you start

- 先读取当前仓库里与书籍目录、命名、链接、附件、索引写法有关的约定，再开始落文件；不要跳过仓库自己的规则，直接拿一套通用模板硬套。
- 先确认这次真的是新书，而不是补写已有书籍笔记；如果 `书籍/` 下已经有同名 md，停下来说明，不重复新建。
- 去重和索引落点只看书籍目录索引与目标文件是否存在；不要为了“学风格”去扫 `书籍/` 下已经存在的正文文件。
- 正文写作必须调用 `/carbon-writer`，并在调用时明确这是一次技术书导读写作：要启用它的导读分支、证据纪律、中文自然度检查，以及分层审校，而不是只拿它随手起稿。
- 如果这次调用已经定义了固定骨架、来源层级、证据格式或 AI 只读区，后续调用 `/carbon-writer` 时要把这些约束一起带过去，不要在写作过程中再起一套平行规则。
- “对当下 Agent 编程的启发”必须基于搜索和思考生成，不得把“听起来合理”硬写成现在仍成立的结论。

## Steps

1. 锁定书名、目标文件和索引落点。
   完成标准：已经确定 `书籍/<书名>.md` 的文件名，以及书籍目录索引里要放到哪个分组；如果用户没有额外限定，默认把“添加书籍”理解成“创建新 md + 补索引”。如果目标文件已存在，直接停下说明，不重复创建，也不改写已有正文。
2. 补齐可查的书目信息。
   完成标准：已经尽量查到作者与原始入口；如果用户没有特别提供版本，默认写当前可验证的最新版本；查不到的字段就留空，不硬猜。
3. 先按固定骨架创建正文，不多不少。
   完成标准：新文件已经按下面这四块顺序建好，不放封面、不留空图片，也不另开“程序员要点”之类的平行区块：

   ```markdown
   # 书名

   - 作者：
   - 版本：
   - 原始入口：[书名](url)
   - 回到索引：[书籍](./README.md)

   ## 个人阅读记录

   > ！AI 不要修改阅读记录这里的内容

   这一节只记我读书时真正被打到的地方。

   ## 对当下 Agent 编程的启发

   ### 已验证的启发

   ### 可能仍有价值的推断

   ## 导读
   ```
4. 生成“对当下 Agent 编程的启发”。
   完成标准：这一节始终存在，并且只围绕当下 Agent 编程及其相邻的 AI 协作 / 软件工程启发来写，不硬往上靠。`### 已验证的启发` 里只放有证据支撑的观点，并为每一条给出可回看的出处；详细展开最多 5 条，更多可简短补充。`### 可能仍有价值的推断` 只放基于材料和证据延伸出来、但暂时还不能写成事实的推断。如果当前确实没有证据支撑的直接启发，就在 `### 已验证的启发` 下明确写：`暂未看到有证据支撑的直接启发。`
5. 用 `carbon-writer` 生成导读。
   完成标准：已经调用 `/carbon-writer` 并使用 `from-scratch` 入口压实材料，同时明确要求它按技术书导读分支来写伴读，不写成抽象书评；如果本 skill 已经定义了固定骨架、来源层级、证据格式或 AI 只读区，也已经一起告诉它必须遵守。导读至少已经说清：这本书在处理什么问题、今天最容易被误解成什么、为什么值得当前读者读、第一次阅读该抓哪几根线。只有章节差异真的会影响阅读路径时，才补 `### 按章导读`；这一块默认写成“章节 / 建议 / 原因 / 与今天的关系”的决策表，而不是章节摘要。
6. 更新书籍索引。
   完成标准：书籍目录索引已经新增对应条目，至少包含名称和一句话注释；如果正文已创建，再补上本地笔记链接。

## `对当下 Agent 编程的启发` 的证据规则

### 来源层级

- 先从官方开发者 / 工程来源开始：优先看 `Anthropic Blog`、`OpenAI Developers Blog`、`Google Developers Blog` 里与 agent、AI 编程、工程实践直接相关的材料。
- 官方补充来源可以继续看 `OpenAI Index` 这类更宽的官方发布入口，但它不是替代开发者博客的第一起点。
- 实践者来源第二层：`Matt Pocock / aihero.dev`、`Simon Willison` 这类长期做 AI 编程实践的人可以作为高质量实践来源；只有在他们明确讨论过某个观点或案例时，才把它写进 `已验证的启发`。
- 发现入口第三层：`AIHot` 的 `论文研究` 区可以帮助发现线索，但最终落笔时要回到原论文、原项目仓库或原始官方文章。`AIHot` 的非论文模块不进强证据池。
- 如果这些推荐起点还不够，就继续扩到更广的一手或准一手来源，例如官方文档、官方工程博客、原论文、作者文章 / 演讲、项目仓库、产品说明、技术组织博客；不要因为起点列表有限，就把搜索范围卡死。

### 证据门槛

- `已验证的启发` 允许由一条足够直接、足够强的一手或准一手材料支撑；不要求机械地凑两条来源。
- 每一条 `已验证的启发` 至少交代三件事：`启发点`、`它和当下 Agent 编程的关系`、`证据或出处`。
- 如果能找到公开项目、GitHub 仓库、skill、工具文档或产品材料里的明确采用，优先使用这类采用证据；文章和博客可以继续承担 framing 或补充解释。
- 如果高质量来源明确讨论过某个旧理念为什么今天仍有价值，即使暂时没找到具体仓库采用，也可以进 `已验证的启发`；但不要把“被明确讨论过”伪装成“已经被广泛采用”。
- `可能仍有价值的推断` 也必须写清楚它是基于哪些事实、材料或证据推出来的；只是不能把它偷渡成已验证结论。

### 落笔规则

- 来源冲突时先信一手来源；如果强来源之间仍有分歧，就把分歧写出来，不要硬裁成单一共识。
- 只看到一个聚合页、二手转述或一句模糊印象时，不要直接下结论。
- 如果没搜到足够支撑，就少写、留空，或者只在 `### 可能仍有价值的推断` 里保守表达；不要靠文风把空白补满。
- 这一节只服务“这本技术书对今天的 Agent 编程还有什么用”这个问题，不要把它写成泛泛的程序员感想，或把书里每个概念都硬往 Agent 上贴。

## Finish

- 确认没有改写 `## 个人阅读记录` 区，也没有替用户补封面。
- 确认这次没有为了模仿语气去读取其他 `书籍/*.md` 正文。
- 确认正文和索引都使用标准 Markdown 相对路径，不依赖 Obsidian 双链承载关键结构。
- 确认“对当下 Agent 编程的启发”里，事实、证据和推断各自在该在的位置，没有硬编。
- 确认 `已验证的启发` 的每一条都已经说清启发点、和当下 Agent 编程的关系，以及可回看的证据或出处。
- 确认 `可能仍有价值的推断` 里的内容都显式写成推断，并交代了它站在哪些已知事实之上。
- 确认导读读起来像一个中文程序员在带读，而不是抽象书评、术语体操，或故意捏出来的“有判断感”句子。
- 确认这次产出同时包含新书籍 md 和对应的 README 索引条目，而不是只做其中一半。
