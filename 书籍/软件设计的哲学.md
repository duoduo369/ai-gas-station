## 对当下 Agent 编程的启发

### 已验证的启发

- **先把 agent 做深，再谈把 agent 做多。**
  Ousterhout 反复强调深模块：接口简单，但背后藏住大量实现复杂度。OpenAI 现在的 Agents SDK 也明确建议先从一个 focused agent 开始，只在确实需要不同 ownership、instructions、tools 或 approval policy 时再拆更多 agent。放到 Agent 编程里，这几乎是在提醒同一件事：别急着增加层数和角色，先看当前接口到底藏住了多少复杂度。
  出处：[Software Design Book](https://web.stanford.edu/~ouster/cgi-bin/book.php)、[Discussion of "A Philosophy of Software Design"](https://web.stanford.edu/~ouster/cs190-winter22/lectures/aposd/)、[Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)

- **tool schema 和 structured outputs，本质上是在给 agent 建“窄接口”。**
  这本书最值钱的一刀，是别把复杂度摊给调用方。OpenAI 的 function calling 和 structured outputs 都要求你用 JSON schema 把输入输出约束清楚，这会逼设计者先决定什么是外部真的需要知道的，什么应该留在实现里消化。对 agent 来说，schema 不是附属文档，而是接口深度的一部分。
  出处：[Function calling](https://developers.openai.com/api/docs/guides/function-calling)、[Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

- **agent 工作流也会长出浅模块，尤其是在 wrapper、透传和分层过多的时候。**
  Ousterhout 对浅模块、透传接口和重复抽象的批评，放到今天的 agent 系统里依然很准。一个看起来分层清楚的 workflow，如果只是多加了几层 prompt 包装、状态转发和参数透传，却没有真正藏住复杂度，那它并没有变深，只是把复杂度搬到了更多地方。
  出处：[Software Design Book](https://web.stanford.edu/~ouster/cgi-bin/book.php)、[Discussion of "A Philosophy of Software Design"](https://web.stanford.edu/~ouster/cs190-winter22/lectures/aposd/)

- **guardrails 和 human review 是在把危险复杂度下沉，而不是给流程加装饰。**
  Ousterhout 讲的是“把复杂度装进少数地方”，不要把边界条件和特例复制到每个调用方。OpenAI 的 guardrails 和 human review 也在做类似的事：把校验、暂停、批准这些高风险判断放进明确控制点，而不是让每个下游 agent 自己临场发挥。这样做的价值，不只是更安全，也是让外围调用更浅、更明显。
  出处：[Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)、[Building agents](https://developers.openai.com/tracks/building-agents)

### 可能仍有价值的推断

- 如果未来项目里的 prompt、tool schema、memory state 和 approval policy 越来越多，那么“深模块”这套尺子可能会直接变成评估 agent 设计质量的核心标准，而不只是传统代码设计原则。
- 很多今天看起来像“模型不够聪明”的问题，最后未必是模型能力问题，也可能只是接口太浅、透传太多、关键信息没有被压进少数稳定模块里。
- AI 时代的战略编程，可能首先不是多写架构文档，而是更早决定哪些复杂度该沉到 harness、skill、tool schema 或 workflow 里，哪些绝不能继续暴露给每个 ticket 和每次调用。

## 导读

这本书在解决的，不是“代码怎样看起来更优雅”，而是一个更硬的问题：复杂度到底该放在哪。Ousterhout 的主张很清楚，软件设计不是追求局部整洁，也不是把函数拆得越短越显得专业，而是想办法让系统的大部分地方保持简单，把真正躲不开的复杂度压进少数接口清楚、实现很深的模块里。

所以它最容易被读偏成两种书。第一种是把它读成一套散装原则，比如深模块、信息隐藏、先写注释、设计两次，各背一条。第二种是把它读成一本和《代码整洁之道》对着干的书，只盯“长函数也可以”“注释并不原罪”这些争议点。这样读都能记住一点东西，但会把它真正的主线读散。它整本书其实都在围着同一件事转：一段设计到底是在消灭复杂度，还是只是在搬运复杂度。

它今天仍然值得读，是因为 Agent 编程让“战术上先跑通”变得更容易了。模型很擅长补代码、补测试、补样板，也很擅长沿着现有结构继续加一层 wrapper、再透传几个参数、再拆一个短函数。问题是，这类产出通常会让复杂度继续留在表面。你会得到更多看起来规整的代码，却不一定得到更深的接口、更低的认知负荷，或者更少的信息泄露。

第一次读，我建议先抓四根线，不要一上来平均用力：

1. `复杂度的症状`：先抓住变更放大、认知负荷和 obscurity，不然你后面很难判断哪些设计动作真的在变简单。
2. `深模块 / 信息隐藏 / 不同层级不同抽象`：这是全书最核心的一束，很多章节都只是从不同角度替它补刀。
3. `战略编程`：把“能工作不够”读成设计节奏，而不是理想主义口号。
4. `决定什么是重要的`：第二版新增这一章以后，全书的很多分散原则会一下子收束起来。

### 按章导读

| 章节 | 建议 | 原因 | 与今天的关系 |
| --- | --- | --- | --- |
| 第 1-3 章 | 慢读 | 先把复杂度的症状和“战略编程”这套立场读稳，不然后面容易只剩技巧。 | 很适合校准今天常见的“先让 agent 写出来再说”心态。 |
| 第 4-8 章 | 精读 | 深模块、信息隐藏、通用模块、更高层抽象和下沉复杂度，基本是全书硬骨架。 | 对 tool 设计、skill 设计、API 边界和 code review 都最直接。 |
| 第 9-15 章 | 带着代码经验读 | 这一段会不断碰到你过去吸收过的“整洁代码”经验，最适合拿真实项目来对照。 | 很适合看清 agent 生成代码为什么常常“整洁但更浅”。 |
| 第 16-18 章 | 必读 | 修改旧代码、一致性和 obviousness，决定这本书是不是能落到日常维护上。 | 对 AI 协作尤其重要，因为大多数真实工作都不是从零开始。 |
| 第 19-21 章 | 第二版重点读 | 第二版真正新增和加厚的价值，主要集中在这里和第 6 章的补强。 | “决定什么是重要的” 很适合直接拿来压今天的 spec、ticket 和 review。 |

如果只想先带着一个不容易跑偏的角度进去，我会建议把这本书当成一本“复杂度归宿学”，而不是一本代码风格书。读的时候一直问自己：这个设计动作是在真正消灭复杂度，还是只是把复杂度从实现挪到了接口、从模块挪到了调用方、从今天挪到了未来。只要这个问题一直在，书里的大多数章节都会自己串起来。
