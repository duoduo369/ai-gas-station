## 对当下 Agent 编程的启发

### 已验证的启发

- **先把领域词汇和关键决策 grill 清楚，再让 agent 往下做，通常比直接开工更稳。**
  `grill-with-docs` 的定位不是写代码，而是先在同一个 session 里把计划和设计问透，同时把已经坐实的术语与决策落进 `CONTEXT.md` 和 ADR。把它和 DDD 放在一起看，几乎就是在重复同一个提醒：真正该先收拢的不是代码骨架，而是团队到底在描述什么、用什么词描述、哪些决策已经定了。对 Agent 编程来说，这很像把“统一语言”和“模型先于实现”从理念，压成执行前的固定动作。
  出处：[grill-with-docs docs](https://github.com/mattpocock/skills/blob/main/docs/engineering/grill-with-docs.md)、[engineering README](https://github.com/mattpocock/skills/blob/main/skills/engineering/README.md)、[DDD Reference](https://www.domainlanguage.com/ddd/reference/)

- **大任务要先拆成“还没决定什么”，而不是“准备做什么”；这很像把战略设计前置。**
  `wayfinder` 明确把自己定义成多 session 的规划流：它处理的是大到一轮 session 装不下、路线还发雾的努力，而且默认“只规划，不执行”；每张 ticket 解决的是一个决策，不是一个实现切片。这个思路和 DDD 后半本的战略设计很搭，因为它逼你先把边界、路线和关键选择讲明白，再进入规格和实现，而不是让 agent 一边写一边替你决定系统边界。
  出处：[wayfinder docs](https://github.com/mattpocock/skills/blob/main/docs/engineering/wayfinder.md)、[wayfinder SKILL](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)、[DDD Reference](https://www.domainlanguage.com/ddd/reference/)

- **统一语言要进入 prompt、tool schema 和输出 schema，不能只停在讨论里。**
  Evans 在 DDD 里把 Ubiquitous Language 放在模型演进的中心；当前 agent 平台又把函数定义、参数 schema 和结构化输出当成运行时契约。放到 Agent 编程里，这给我的提醒很直接：领域词汇如果没有落到可执行接口里，agent 很容易把“业务上是同一个东西”的概念说散、做散。
  出处：[DDD Reference](https://www.domainlanguage.com/ddd/reference/)、[Function calling](https://developers.openai.com/api/docs/guides/function-calling)、[Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

- **多 agent 不等于多分工，先要有清楚的边界上下文。**
  DDD 一开始就强调模型总有适用边界，离开上下文，同一个词会变形。现在的 agent 编排文档也明确建议：specialist 要拿窄职责，只有当下一段工作真的需要不同的 instructions、tools 或 policy 时才拆分。比起先问“要不要多加几个 agent”，更该先问“这个 agent 究竟在什么语境里负责什么”。
  出处：[DDD Reference](https://www.domainlanguage.com/ddd/reference/)、[Context Mapping with an AI-based Component](https://www.domainlanguage.com/articles/context-mapping-an-ai-based-component/)、[Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration)、[Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)

- **把 LLM 当成系统里的一个组件来设计，通常比把它当万能中枢更稳。**
  这不是硬往今天靠。Eric Evans 现在还在直接讨论 “AI-based component” 的 context mapping，Domain Language 首页也已经把“帮助组织把 LLM 集成进 domain-rich systems，同时保住设计完整性”写成当前重点。这个信号很强：AI 进入系统后，首先要谈的不是它能不能一把梭，而是它和既有模型、流程、责任边界怎么接。
  出处：[Domain Language](https://www.domainlanguage.com/)、[Context Mapping with an AI-based Component](https://www.domainlanguage.com/articles/context-mapping-an-ai-based-component/)

- **一旦 agent 能执行写操作，就要补上一致性边界、审批和停顿点。**
  DDD 对 aggregate 的讨论，本来就在处理事务边界、并发和分布式带来的复杂性。今天的 agent SDK 也把 approval、guardrail、pause before side effects 当成一等能力。换成 Agent 编程的话，这更像一条设计纪律：不要让模型跨着几个业务对象一路写到底，先把“哪一步算一次允许发生的状态变化”界出来，再决定哪些动作必须经过人或规则批准。
  出处：[DDD Reference](https://www.domainlanguage.com/ddd/reference/)、[Aggregates Preview](https://elearn.domainlanguage.com/preview/aggregates-preview/)、[Agents SDK](https://developers.openai.com/api/docs/guides/agents)、[Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)

### 可能仍有价值的推断

- 如果团队以后真把 agent 当长期协作者，`context map + ubiquitous language + tool schema` 很可能会一起变成要版本化维护的项目资产，而不只是散落在 prompt 里的临时约定。
- DDD 里的 core domain / supporting domain 区分，可能很适合拿来决定哪些链路要重投 eval、guardrail 和 human review，哪些地方只把 AI 当提效工具。
- 很多“agent 不稳定”的问题，最后未必只是模型能力不够，也可能是领域词汇、边界、审批链路和状态边界没有先定义清楚。

## 导读

这本书要处理的，不是“怎么给软件项目套一组新名词”，而是一个更根上的问题：当业务本身很复杂、团队里又有产品、业务专家、开发、测试、运维各说各话时，软件怎样还能围着同一个模型持续演化。Evans 给出的答案不是先讲框架，也不是先讲架构图，而是先把模型、语言和实现重新绑回到一起。

今天最容易把它读偏成三样东西：一是实体、值对象、聚合、仓储的名词表；二是“按领域拆微服务”的前置教材；三是“先列几个业务对象，再让 AI 生成代码”的提示词素材。这样读都能抄到一点东西，但会把这本书最值钱的部分读丢。它最重要的提醒其实很朴素：复杂度不只是长在业务里，也长在团队对业务的说法、代码里的命名、模型的边界，以及系统整体的取舍里。

它现在仍值得读，恰恰是因为今天写软件更容易被“实现速度”带偏。AI 把写代码、补测试、搭脚手架这些动作压得更快了，但模型不会因为生成速度变快就自动变清楚，边界也不会因为服务拆得更细就自然切对。这本书一直在逼你回到慢问题上：我们到底在描述什么业务现实？团队有没有围着同一个模型协作？哪些地方值得深建模，哪些地方只要够用？

第一次读，我建议先抓四根线，不要一上来就平均用力：

1. `知识消化 -> 深层模型`：先看模型是怎么从业务理解里长出来的，不是怎么从类图里拼出来的。
2. `统一语言 -> 模型驱动设计`：盯住语言怎样进入命名、代码和讨论，不要把它读成“沟通要顺畅”的空话。
3. `构造块`：Entity、Value Object、Aggregate、Repository 都当工具看，边读边对照手头系统里实际遇到的问题，不必背术语。
4. `战略设计`：后半本一定要留精力给边界上下文、模型完整性、核心域和大比例结构；这部分最容易在“DDD 入门”阅读里被轻轻带过，但它对今天的系统设计更要命。

| 第一部分：运用领域模型 | 慢读 | 这部分在回答“为什么要把模型放回软件中心”，也是全书主线的起点。 | 如果今天你常把 prompt、PRD、代码和测试当成四份互不相干的文本，这一部分最容易打到你。 |

如果只想先建立对这本书的正确认识，我会把目标放低一点：先别急着学会 DDD，先别把 DDD 读窄。先读出它在反对什么，读出它为什么一直盯着语言、模型和边界不放。等这三根主线立住，再回头看那些常被单独拿出来讲的战术模式，你会更容易知道它们是在保护什么，而不是只记住它们叫什么。
