# T-001 粗目录树原型

> 用途：对齐第一版顶层目录，不是最终规范文档。
> 当前判断：仓库更像“对象类型为主 + 横切目录补充”，而不是“资源/知识”分层仓库。

## 方案 A：轻量混合（推荐）

```text
AI加油站/
├─ README.md
├─ AGENTS.md
├─ CONTEXT.md
├─ 书籍/
│  ├─ README.md
│  └─ 单本学习笔记.md
├─ 演讲/
│  ├─ README.md
│  └─ 单场学习笔记.md
├─ skills/
│  ├─ README.md
│  └─ 某个 agent skill 的学习记录.md
├─ playbook/
│  └─ README.md
├─ assets/
├─ 收件箱/
│  └─ README.md
└─ docs/
   ├─ conventions.md
   └─ wayfinder/
      ├─ MAP.md
      └─ tickets/
```

### 适合你的原因

- 直接匹配你说的 awesome 风格：对象目录自己承载索引与深度笔记。
- 顶层足够短，Obsidian 左侧看起来直观。
- `资源/` 不再单列，避免“既有书籍/演讲，又有资源/”的重复分层。
- `收件箱/` 给临时沉淀留缓冲，不至于因为结构没想清而把内容堆根目录。

### 风险

- 如果后面出现大量“不属于书/演讲/skills”的主题型笔记，可能还要再补一个目录。

## 方案 B：保留资源层

```text
AI加油站/
├─ README.md
├─ AGENTS.md
├─ CONTEXT.md
├─ 资源/
│  ├─ 书籍.md
│  ├─ 演讲.md
│  └─ skills.md
├─ 书籍/
├─ 演讲/
├─ skills/
├─ playbook/
├─ assets/
└─ docs/
```

### 优点

- “资源索引层”概念清楚。

### 问题

- 很容易重复：`资源/书籍.md` 和 `书籍/README.md` 本质都在做索引。
- 你现在的使用描述已经更偏向“对象目录自带索引”，保留 `资源/` 反而绕。

## 方案 C：轻量混合 + 主题目录

```text
AI加油站/
├─ README.md
├─ AGENTS.md
├─ CONTEXT.md
├─ 书籍/
├─ 演讲/
├─ skills/
├─ 主题/
├─ playbook/
├─ assets/
└─ docs/
```

### 适用场景

- 你明确知道会持续写一些不依附于具体书/演讲/skill 的主题型笔记，比如“提示词设计”“AI 编程协作心法”。

### 问题

- 第一版可能仍然偏早，容易先建空目录。

## 当前推荐结论

第一版采用 **方案 A**，并明确：

- 顶层不单列 `资源/`；
- 先只建已经高频且明确的对象目录：`书籍/`、`演讲/`、`skills/`；
- `skills/` 只承接 agent skills 的学习与复盘；
- `playbook/`、`assets/`、`docs/` 作为横切目录保留；
- 增加一个 `收件箱/` 作为未分类内容的缓冲区；
- `主题/` 先不建，等后续确实反复出现再升为顶层。

## 这张原型要确认的点

1. `收件箱/` 要不要作为第一版顶层目录；
2. `主题/` 是现在就建，还是等内容真正出现再建；
3. 顶层对象目录是否只保留 `书籍/`、`演讲/`、`skills/` 三个。
